## Recommendation

**Per-version mechanism**

- **PHPUnit 12.5**: prefer overriding `protected function invokeTestMethod(string $methodName, array $testArguments): mixed` in a shared base `TestCase` (or trait applied to it). It is the cleanest hook: `setUp()`/preconditions run untouched and see the real method name throughout (no property mutation is ever visible to user code), and skipping is a plain early return (`addToAssertionCount($n)` / `expectNotToPerformAssertions()` then `return null`) instead of `parent::invokeTestMethod(...)`. The one side effect (`CustomTestMethodInvocationUsed` event fires for the whole class) is currently silent in stock PHPUnit 12.5.34's CLI reporter, but that is an implementation detail of this PHPUnit release, not a documented guarantee — do not rely on it staying silent across PHPUnit releases.
- **PHPUnit 11.5**: `invokeTestMethod()` does not exist as a hook (`runTest()` is `private` and calls `$this->{$this->methodName}(...)` inline), so use the reflection fallback: a `#[Before]` method that, when the test id is in the replay map, uses `ReflectionProperty(TestCase::class, 'methodName')` to point at a stub method; the stub restores the original name and then injects the assertion count. `#[Before]` is the correct phase — it fires before `setUp()` and well before `runTest()`, so the swap is in place by the time `runTest()` resolves `$this->methodName`. Trade-off versus approach A: for the duration of `setUp()` itself, `$this->name()`/`$this->methodName` reports the stub name, not the real one, for replayed tests — harmless for stock PHPUnit fixture code, but a landmine if `setUp()` (yours or a parent trait's) branches on the test name.
- **Both versions with one implementation**: approach B (reflection + `#[Before]`) was verified to work identically, unmodified, on both 12.5.34 and 11.5.56 (row C1). If a single code path across versions is wanted, use approach B everywhere; use approach A only where the cleaner "`setUp()` never sees a fake name" property matters and 11.5 support is not needed.

**What must never be replayed**

- **Tests using `expectException()`/`expectExceptionMessage()`/`expectExceptionCode()`/`expectExceptionObject()`.** Both mechanisms replay them as a *silent* pass with no exception ever verified (rows A4, B4) — not a hard failure, not a risky flag, not a warning, even with every `--fail-on-*`/`--display-*` flag enabled. There is no runtime-inspectable signal to auto-detect this before the body would run: `expectedException` (and siblings) are `private` properties on `TestCase` with no public getter, and they are only populated once the (skipped) body actually calls `expectException()`. The only reliable guard is **static exclusion**: build the replay map (or an exclusion list) by scanning test method source/AST for calls to `expectException*`, or maintain an explicit allowlist/denylist convention, never by asking the framework at runtime.
- **Tests other tests `#[Depends]` on.** A replayed test still reports "success" so dependents are not skipped, but the stub's `return null` (or whatever the trait's fixed return is) is what dependents receive as their injected argument — the real return value is gone (row B5). Either never replay a depended-upon test, or make the trait replay the *actual* cached return value too (not just the assertion count) if dependents must keep working.
- **Data-provider sets are addressed individually** (`Class::method#N` via `valueObjectForEvents()->id()`), so replaying one set (e.g. `#0`) while letting others run for real works cleanly (rows A1/B1) — no special exclusion needed there beyond correct id bookkeeping.
- **`setUp()`/`tearDown()`/`#[Before]`/`#[PreCondition]`/etc. can never be skipped** by either mechanism — only the test method body itself is skippable, at the earliest via `invokeTestMethod()` (12.5) or via the method-name swap consulted at `runTest()` time (11.5/12.5). If expensive fixture work needs to be skipped too, expose an `isReplaying()` guard computed in the base class's own `setUp()`, and make it throw (not guess) if consulted before `parent::setUp()` ran (rows D1-D3) — this turns a subclassing mistake into a loud test error instead of a silently-wrong optimization.
