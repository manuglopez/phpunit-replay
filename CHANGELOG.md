# Changelog

All notable changes to this project will be documented in this file.

## [Unreleased]

### Changed

- **Migrations now select by whether the test database runs them, and each test file keeps the tables it actually queried.** Until 0.12, every test file whose class used `RefreshDatabase`, `DatabaseMigrations` or `DatabaseTransactions` was recorded as touching every table any migration names (`LaravelIntegration::augment()`, inherited from Pest). Every database test file therefore held the same set of tables: 159 on one real project and 111 on another. The `Migration` rule selected by table over that set, so in practice it selected every database test file for every migration, whatever the migration touched. On a project with a schema dump it also selected for migrations that never run in tests: Laravel loads the dump and then runs only the migrations its `migrations` rows do not list, and on one real project 122 of its 124 migrations were already in the dump. With the new default, `migrations => 'precise'`:
  - **A squashed migration** is one listed in the `migrations` rows of the schema dump the test connection loads. It selects nothing, because no test database runs it, and `explain` / `--dry-run` say so: `database/migrations/…_create_posts_table.php ← Migration squashed into database/schema/sqlite-schema.sql, not run by tests: selects nothing`. The test connection is read from the PHPUnit configuration's `DB_CONNECTION`, then `.env.testing`, `.env` and the default in `config/database.php`. Laravel loads `database/schema/{connection}-schema.dump`, else `.sql`. If the rows cannot be read, or the connection is unknown, nothing counts as squashed.
  - **Any other migration is pending.** It selects every test file that uses a database, whichever tables it names: every fresh test database runs it, and a migration that throws breaks all of them. That set now includes database test files that recorded no table at all.
  - **`test_tables` holds only what each test file queried.** Which files use a database is stored apart, as `uses_database` in the graph. The new field is additive: older readers ignore it, and a graph without it still counts every file that recorded a table.

  Measured on the `laravel-lite` fixture with a SQLite schema dump that lists all three of its migrations, plus one test file that builds its own table in `setUp()` (5 test files, 4 of them database tests), with `run --dry-run`:

  | change | 0.12.2 | 0.13.0 |
  |---|---|---|
  | edit the squashed `create_posts_table` migration | 3 (by table, over the union) | 0 (`squashed into …`) |
  | add a pending migration that names no table | 5 (every test) | 4 (every database test) |
  | add a pending migration that alters `posts` | 3 (the union's holders; the `setUp()` table test was missed) | 4 (every database test) |
  | change the `ledgers` block of the dump | 0 | 1 (`LedgerTest`) |
  | change the `posts` block of the dump | 0 | 2 (`PostJsonTest`, `PostsIndexTest`) |

  A pending migration that names a table now selects every database test, which can be more than 0.12 selected: it runs in every fresh test database whichever table it names.

  **`migrations => 'conservative'`** restores the 0.12 behaviour: the union of every migration table at recording time, and selection by table intersection. Use it when a test reaches the database in a way the table tracker cannot see. In that mode, a migration that names a table the extractor cannot read (`Schema::create($tableNames['roles'], …)`, `DB::table($table)`) now selects every database test file instead of narrowing by the tables it could read.

  **One-time cost: the first run after upgrading re-executes every cached test file once**, on each branch the first time that branch runs. The non-edge input digest's version token moves from `n3` to `n4` (new `schema:`, `migrations:pending`, `migrations:unknown` and `sibling-tree:` scopes), so no result stamped by an earlier version matches. The same run replaces each executed file's inflated `test_tables` with what it queried. A database test file that queries no table in that run keeps its old set, which only ever selects more.

  **Known limit (review point):** a query whose result an earlier test cached in a static (a memoized setting, a `once()` value) runs only in the first test of the process that needs it, so only that test file records the table. Later test files that read the cached value do not. Recordings converge over runs as the first loader varies, but a single run can miss a reader. Queries made through raw PDO, or by a seeder `RefreshDatabase` runs before the application hook fires, are not recorded either. `conservative` avoids all three at the 0.12 price.

### Added

- **A change to the schema dump selects the tests that use the tables it changed.** `php artisan schema:dump` writes `database/schema/{connection}-schema.sql` (`.dump` for a `pg_dump` archive). `RefreshDatabase` builds every test database from it before running any migration, coverage never credits it to a test, and it is not a migration, so until 0.12 no rule claimed it: editing or regenerating it ran nothing and replayed every result. The new `SchemaDump` rule compares the dump at the change set's base (`git show <base>:<path>`) with the working tree's, table by table:
  - a table whose block was added, removed or changed selects the test files that recorded it, plus every database test file that recorded no table: `tests/Feature/PostJsonTest.php ← SchemaDump database/schema/sqlite-schema.sql (posts)`;
  - a changed table no test records, or a changed statement no table owns (a function, a type), selects every database test file;
  - a change to the `migrations` rows alone selects nothing beyond what the migration files changed with it select;
  - a dump that does not parse, including a binary `pg_dump -Fc` archive, a dump with no version at the base, or a change set with no base, selects every database test file. While the graph records no table, it selects every test.

  A block is every statement about the table. The parser covers the dialects as Laravel writes them: MySQL and MariaDB (backquoted `CREATE TABLE`, `/*!NNNNN …*/` executable comments, `DELIMITER` trigger and routine blocks, backslash escapes); PostgreSQL (`CREATE TABLE public.t`, and `ALTER TABLE ONLY public.t ADD CONSTRAINT …`, `CREATE INDEX … ON public.t`, triggers, owned sequences, all attributed to `t`, with `$$` quoting, psql `\restrict` lines and `COPY … FROM stdin` rows); SQLite (`CREATE TABLE IF NOT EXISTS "t"`, `CREATE INDEX … on "t"`, `BEGIN … END` triggers). Comments and whitespace outside quotes do not count, so re-dumping an unchanged schema changes nothing. The digest mirrors the rule per test file: `schema:<dump>@1` holds the dump's global statements, the blocks of the tables that file records, and the blocks of the tables no test records (every block for a database test file with no recorded table). A dump that does not parse is hashed whole. A test file's stamp therefore moves only when a table it depends on changes. On `laravel-lite`, changing the `ledgers` block selects `LedgerTest` only, and changing `posts` selects the two test files that query `posts`, not `UserModelTest`; the digests of exactly those files move.
- **Migrations in every directory the application loads them from.** The `Migration` rule claimed only `database/migrations/**/*.php`; a migration in `database/tenant`, a module, or any path a provider passes to `loadMigrationsFrom()` was attributed by coverage to whichever test first ran it, or to nothing. The rule now covers, besides `database/migrations`:
  - the new **`migration_paths`** config key (default `['database/migrations']`);
  - every **literal** `loadMigrationsFrom()` argument in `app/Providers/**` and `bootstrap/**` (not `bootstrap/cache`): a string, an array of strings, `database_path('…')`, `base_path('…')`, or `__DIR__` / `dirname(__DIR__, n)` concatenated with strings, read with php-parser. An argument built any other way (a variable, a method call, `config()`) is ignored, never guessed: list that directory in `migration_paths`;
  - `database/migrations/tenant` when `stancl/tenancy` is in `composer.lock` (its documented default). `spatie/laravel-multitenancy` documents no default path of its own, so nothing is added for it.

  Each path also gets the fallback `database/migrations/**` has: a non-`.php` file under it runs every test.
- **A new file in a new subdirectory of a sibling directory selects the tests next to it.** A new `app/Console/Commands/Reports/SendReport.php`, with no tested file under `Reports/` yet, selected nothing: the `Sibling` rule looked only at the file's own directory. It now walks up to the nearest ancestor directory, up to and including the sibling root (`app/Console/Commands`), under which some test has an edge, and selects the tests with an edge anywhere under it: `tests/Feature/PruneUsersTest.php ← Sibling app/Console/Commands/Reports/SendReport.php (app/Console/Commands/**)`. The walk stops at the first ancestor with edges, and a file with none up to the root is still left to the other rules. Mirrored in the digest as `sibling-tree:<dir>@1`.

### Fixed

- **Fix: the tables a test touched in `setUp()` were never recorded.** The table tracker was armed at `Test\Prepared`, which fires after `setUp()` returns, so the queries of a `setUp()` and its factories were invisible. That is why the 0.12 union of every migration table was load-bearing. The trackers are now armed inside `setUp()`, through Laravel's `afterApplicationCreated()` hook, right after the application and the testing traits are set up. A Laravel test case is found on the call stack at `Test\PreparationStarted`, because PHPUnit dispatches events synchronously. `Prepared` still arms any application the hook never saw. On `laravel-lite`, a test that creates and fills its own table in `setUp()` recorded no table and now records it.
- **Fix: the in-process extension recorded no table and no template edge.** With the extension registered in `phpunit.xml` and no wrapper, the Laravel trackers were never registered, so `test_tables` stayed empty, and a test rendering a Blade template got no edge to it: a template change could only reach it through the `resources/views/**` fallback, which runs every test. The in-process extension now registers the same trackers and the same uses-database collector as the wrapper's PHPUnit child, and both write the same `test_tables` and `uses_database` for the same suite, checked on `laravel-lite`.
- **Fix: a database test was not recognised through a trait of a trait.** Only traits used directly by the class or an ancestor counted, so `LazilyRefreshDatabase` (which uses `RefreshDatabase`) and a project's own testing trait were missed, and `DatabaseTruncation` was not in the list. All four Laravel traits now count wherever they sit in the trait tree.
- **Fix: `DB::table('posts as p')` in a migration was read as a table named `posts as p`.** The alias is dropped.

Content keys, fingerprint composition and the remote layout are unchanged. The graph file gains an optional top-level `uses_database`, written only when non-empty, which older readers ignore.

## [0.12.4] — 2026-10-02

### Fixed

- **Fix: PHPUnit 13.4 broke the wrapper and static analysis for everyone on `^13.0`.** 13.4.0 gave `XmlConfiguration\Loader`, `CliArguments\Builder` and `Configuration\Merger` a required `Event\Emitter` constructor argument; they used to take none. phpunit-replay constructed all three with no arguments, to read the project's PHPUnit configuration, so on 13.4 every wrapper command died with `phpunit-replay: unexpected error (Too few arguments to function PHPUnit\TextUI\XmlConfiguration\Loader::__construct(), 0 passed in …/ProjectLocator.php on line 77 and exactly 1 expected): degrading to a plain PHPUnit run`: tests ran, nothing was recorded or replayed. PHPStan reported the same thing on a fresh `composer update` (`Class PHPUnit\TextUI\XmlConfiguration\Loader constructor invoked with 0 parameters, 1 required`, and the same for `CliArguments\Builder` and `Configuration\Merger`). The three are now constructed in one place, `PHPUnit\ConfigurationReader`, which reads the installed constructor and passes PHPUnit's own emitter (`Event\Facade::emitter()`, what `TextUI\Application` passes) only when one is required; 11.5, 12 and 13.0-13.3 are constructed exactly as before.

### Known

- **Parallel runs (`--parallel`) on PHPUnit 13.4 need a ParaTest release that supports it.** ParaTest 7.25.0, the latest, accepts `phpunit/phpunit ^13.3.4` but still constructs `PhpHandler` with no arguments, so on 13.4 it dies with `ArgumentCountError`, exit 255, before any test runs (plain `vendor/bin/paratest` fails the same way). Until a fixed ParaTest ships, phpunit-replay prints `phpunit-replay: ParaTest <version> cannot run on PHPUnit <version> (an upstream incompatibility, not a test failure). Run without --parallel, or pin phpunit/phpunit below <version> until ParaTest supports it.` after ParaTest's output. The exit code stays non-zero and nothing is recorded or replayed from that pass. The message is printed only when output is captured; a run attached to a terminal shows ParaTest's own fatal alone.

## [0.12.3] — 2026-10-02

### Fixed

- **Fix: `record --allow-ci-baseline` died with `Unknown option`.** A CI job seeding a baseline ran `vendor/bin/phpunit-replay record --fresh -p --allow-ci-baseline` and got `phpunit-replay: unexpected error (Unknown option "--allow-ci-baseline". Most similar options are --ignore-baseline, --generate-baseline, --use-baseline, --fail-on-warning, ...)`, exit code 2. Only `run` defined the option, so the wrapper forwarded it to PHPUnit, and `record` hardcoded it off, although `record` is the command CI uses to publish a baseline. `record` now takes `--allow-ci-baseline` with `run`'s meaning: in CI it finalizes and publishes the baseline; without it, CI still saves results but publishes nothing. `verify` does not take it: it is a pure measurement and never finalizes a baseline.
- **Fix: a wrapper option on the wrong command produced a misleading PHPUnit error.** An option that belongs to another phpunit-replay command was forwarded to PHPUnit, whose "Most similar options" list pointed at PHPUnit's own baseline flags. It now fails before PHPUnit starts, exit code 2: `phpunit-replay: --allow-ci-baseline is an option of "run" and "record", not of "verify"`. The message is built from the registered commands' option definitions. Options after `--`, PHPUnit's own options, and value-taking options that PHPUnit also defines (`--log-junit=FILE` on `verify`) are still forwarded untouched.

## [0.12.2] — 2026-10-01

### Fixed

- **Fix: a structural change announced a recording that never happened.** After `phpunit-replay.php` changed, a developer's `run` printed `phpunit-replay: structural change (replay_config): the cached baseline cannot be used, recording a fresh baseline`, and then replayed all 11,029 tests from the remote (`0 executed … 11029 replayed (11029 from remote)`). The first line was false. The warning was written as soon as the local graph drifted, before the pipeline had looked at the remote; the remote held a baseline recorded with the new configuration, which was adopted, and nothing was recorded. The warning now states only the fact (`structural change (replay_config): the cached baseline cannot be used`), and the decision is printed once it is known: `adopted the develop baseline (a4416e2) from the remote` when a remote baseline was adopted (this line used to be visible only under `PHPUNIT_REPLAY_DEBUG=1`), or `recording a fresh baseline` when there is no remote, the remote holds none of the candidates, or the remote baseline is structurally drifted too. `--dry-run` prints the same lines as the real run. Behaviour is unchanged: the same baselines are adopted or recorded in the same cases, only the messages differ. The in-process extension is untouched: it pulls from the remote only when it has no local graph, so on a structural change it does record.

## [0.12.1] — 2026-10-01

### Fixed

- **Fix: a single test that errored, rather than failed, kept the whole suite from ever getting a baseline.** PHPUnit exits 2 as soon as one test errors (an uncaught exception, a missing table), against 1 for a failure. The wrapper counted only 0 and 1 as a pass that ran to the end, so a `record` with one erroring test saved its results without a sha. The next pass found no cached baseline and recorded the whole suite again, and so did every pass after it for as long as that test kept erroring. On a real application, three erroring tests in one file were enough to turn a no-change `run` into a full 10,957-test recording. An error is an outcome like a failure: the test ran and its result is recorded, and it re-runs on the next pass like any failure. A pass now counts as complete on exit 0, 1 or 2. Only a run that stopped early (aborted or truncated) or never finished (a crash or a signal) is incomplete. The in-process path never had the problem, because it never looked at the exit code.
- **Fix: `record` announced a baseline it had not saved.** The summary line printed `baseline <branch>@<HEAD>` whether or not the pass finalized one. A CI run without `--allow-ci-baseline`, or an incomplete pass, saves results but no baseline, and the line now leaves the segment out instead of naming a sha the graph does not hold.

## [0.12.0] — 2026-10-01

### Fixed

- **Fix: results recorded on one tree were served on another, in three ways the layer audit could not see.** 0.11.0 made every result layer valid for the tree before serving it, on one premise: that a layer's results were recorded on the tree at the layer's sha. Three ordinary workflows broke that premise, and each printed a green run on a suite plain PHPUnit fails. Reproduced on the `plain` fixture:
  - **A dirty working tree, then another branch.** `main` breaks `Money::add`; an uncommitted fix is run, so `main`'s layer holds passes at the broken sha. The fix is discarded and `git checkout -b other`: `✓ 0 executed · 35 replayed`, exit 0. Only the last-run snapshot knew about the dirty content, and it describes one branch (and is overwritten by the next branch that runs).
  - **Results written without the sha moving.** A CI run without `--allow-ci-baseline` (or an incomplete run) saves its results into the layer and leaves the sha behind. After a `git revert` back to that sha the diff is empty and the reverted tree's passes are served. The same holds for a test that only reads a watched data file, which is not in its content key at all.
  - **A dirty layer, published.** With `remote_push: all` a run on a dirty tree published its graph; another machine, clean at that sha, adopted it: `35 replayed (35 from remote)`.

  **Root cause: a layer trusted that its results ran on its sha's clean tree, and nothing checked that.** Every result now carries a stamp of what it ran on — its content key `k`, which it already stored, and a new **non-edge input digest** `n` — and is served only while both are what the current tree gives its test file. `Select\StampAudit` checks this after `Select\LayerAudit`, for every result any layer would serve, in the wrapper and in-process alike. The digest (`Select\NonEdgeInputs`, the one place it is defined, version token `n3`) hashes every file a non-edge rule would select the test file for: watch patterns, the Laravel `Migration`, `Blade` and `Sibling` rules, the Laravel fallbacks, and the residue. **Each test file's digest leaves out that test file's own dependencies** — those are its key's inputs — so it is a function of the tree and of that test file's own edges alone: another test gaining or losing an edge never moves it. (On a real project's tree, one test gaining one edge used to move the digest of all 726 test files; it now moves one.) A result that fails is masked for the run, never deleted, so a file keeps executing until a complete run replaces every one of its results; `--explain` says which half failed: `tests/MoneyTest.php ← StaleResult content key changed (main@abc1234)`, `… non-edge inputs changed …`, or `… unstamped …`. A stamp records only what the tests provably ran on: a file that changed while they ran leaves its dependents' results unstamped, to run again. A result the in-process extension replayed keeps the stamp it was served with, never this run's. The quarantine uses the same stamp: a status change is a flip only when key **and** digest are unchanged, so a test that fails because a watched file it reads changed is no longer quarantined as flaky.

  **Publishing follows the stamp.** Objects are always publishable, dirty tree or not — an object is addressed by what actually ran, and now carries its digest as `n` (path and `k` unchanged; older readers ignore it). An object holds a variant per digest, the newest at the top level and older ones under `variants`, so the first publisher of a `k` no longer keeps everyone else's digest out. **Objects are therefore no longer append-only:** a publish of a digest the object does not hold rewrites it. Before writing, the publisher asks the remote for the object (one GET per object whose digest is new, not per run) and merges into what the remote holds, never into its own mirror, which can be stale. A git push rejected because another machine pushed first merges each object's variants with the fetched copy instead of taking one side. The rewrites are bounded: a digest whose results are the same as a variant's already held (same test ids, statuses, messages and assertion counts; the usual case when only a watched file every test reads changed) is stored as a one-line alias under `aliases` rather than as a second copy of the results, and an object keeps at most 20 digests in all, the most recent first. An alias records the fingerprint of the outcome it was compared against and serves only while its variant still has it, so a merge that replaces the variant with another machine's different run of the same digest drops the alias instead of serving it a pass its own run never had. The cap counts a variant and its aliases as recent as the newest of them, keeps a variant before its aliases and cuts the oldest aliases first: the variant every alias points at, the only copy of their results, is never the one trimmed. Only results stamped with the current key and digest are published. A remote object serves a test file only with the results it holds under the file's current digest — which also lets it serve a file a watch pattern selected, or one in the run list only because its local result is stale — and an object without `n` keeps the 0.10.1 rule (only files selected through `k`). The branch graph is published only from a working tree clean of anything a result could depend on — a test file, a file some test has an edge to, a path a non-edge scope would hold; a README edit, a tracked file git ignores, or a CI step rewriting `phpunit.xml` (the graph's fingerprint records it as it is) does not count — and carries only the branch's results stamped for that tree. A dirty tree skips the graph with one line naming the files, after a run and in `push --graph`, which still pushes the objects and exits 1. `push` reads the PHPUnit configuration the graph was recorded with, so a baseline recorded with `-c` publishes its objects too.

- **Fix: a watch pattern never fired for a file some test has an edge to.** The PHP-edge rule consumed the file first, so a pattern naming it — "these tests depend on this" — was skipped, and a file whose work coverage credits to the first test that runs it (a migration run once per worker, a config file loaded at boot) selected only that test. Watch patterns now apply to every changed file, and **watch patterns only ever add**: a configured pattern, a fallback and an unattributable file matching the same change have their target lists joined, so a configured key spelled exactly like a fallback default (`'resources/views/**' => [one test]`) adds that test to the fallback's every-test list instead of replacing it: a new template nothing references still runs every test. The residue fallback still applies only to what nothing attributed. With the Laravel rules on, two Laravel defaults become **fallbacks**, patterns that fire only for a file no rule claimed, because the `Blade` and `Migration` rules attribute most of those files per test: `resources/views/**` and `database/migrations/**`. The `Blade` rule now follows static references (`@include`, `@includeFirst`, `@extends`, `@component`, `view('x')`, `<x-name>`) from any changed template, known, new or deleted, to the tests rendering a template that references it. What it cannot attribute still runs every test, as the default always did: a new error page or pagination override, the target of `view('pages.' . $slug)`, an edited plain `.php` view, a template nothing references. The `Migration` rule selects by table. A migration for tables no test records (a new table) runs every test that records a table (not quite every test that uses the database: tables are recorded after `setUp()`, so queries made only in `setUp()`, through raw PDO, or cached statically by an earlier test are not seen), and one it cannot read tables from runs everything. A non-`.php` file under `database/migrations/` (a `.sql` a migration loads) is left to the fallback, which runs everything. With `laravel => 'off'` both defaults stay plain patterns. What this changes: a change to `config/**`, `routes/**`, `lang/**` or any configured pattern now runs every test the pattern maps to, not only the tests with an edge to the file; a change to a template included under a condition runs the tests rendering its parent. Measured on a real project's graph (726 test files, 274 templates), editing one template at a time: 103 templates reach no test through references and fall to the fallback (every test, as 0.11.0); 39 select more tests than 0.11.0 did, because a template's edge tests are now joined by the tests rendering a template that includes it (`components/svg` 50 → 102, `components/application-logo` 52 → 56, a menu partial 43 → 47); none selects fewer; the mean per edit goes from 280.2 to 281.8 test files. The rule reads the tree's references once per pass for all changed templates (0.002 s for 274 changed templates over a cached map, 1.49 s before), from the same `<stateDir>/blade-references.json` the digest uses.

- **Fix: a changed `.php` file that `<source><exclude>` keeps out of coverage selected no test at all.** Coverage never reports it, so it never has an edge, and the rule chain had nothing to select by: an edit to a provider, a middleware, a kernel or an exception handler excluded that way ran nothing, and the next run served every result recorded before it. Such a file now runs every test whatever `static_declaration_edges` says, and whatever watch pattern also names it: a pattern such as `'app/**' => [three tests]` adds those tests and never narrows the selection to them (watch patterns only ever add): an edit to an excluded `AppServiceProvider` runs every test, the three included. A project that wants narrower selection for such a file should take it out of `<source><exclude>`, so that coverage records which tests execute it. It does so even when some test has an edge to it (a static-declaration or once-process edge): that edge says one test depends on it, not that the others do not, so another test gaining such an edge moves only its own digest (`unattributable@3`; on a real project's tree an edge to `app/Console/Kernel.php` used to move all 726 digests, and moves one).

- **Fix: a file whose name is a number (`2024`, `404`) at the project root made every command fail with a `TypeError`.** PHP turns a numeric string array key into an int, and every map keyed by path handed it to a `string` parameter. Paths are now cast back to strings wherever such a map is read. The same goes for a configured watch pattern that is a number (`'404' => 'tests/Feature'`), which `phpunit-replay.php` used to drop silently and `WatchPatterns` refused with a `TypeError`.

  **One-time cost: the first run after upgrading re-executes every cached test file once**, on every branch the first time that branch runs, and stamps the results; the run after replays as before. Every result written by an earlier version carries no digest, and there is no sound way to validate one without it: the key alone does not see a watched file, and the diff from the layer's sha is exactly the premise that failed. A machine can absorb that run from another's fresh objects: a file in the run list only because its result is unstamped is served from an object whose key and digest match. A result served from an object published by an earlier version carries no digest either, so that test file runs once locally on the next run.

  **Cost of the check**, measured on a real project's tree (726 test files, 6,446 files in the working tree): about 0.34–0.38 s per pass (content keys 0.02 s, digests 0.29–0.32 s), and 0.76 s on the first pass on a machine, before its hash cache exists. File hashes now persist across runs in `<stateDir>/content-hashes.json`, keyed by each file's `stat()` and trusted only the way git trusts its index: an entry is written only for a file whose last change is at least two seconds older than the moment it was read, so a later change always shows. That moment is taken from the file system's clock, not the process's, so a network mount whose clock lags cannot make a fresh file look old: once per pass a probe file is written and removed in the state directory when it is on the project's device, else in the repository's git directory, and never in the working tree (with neither on the project's device the cache is off). The cache relies on `ctime`, which a process cannot set on a local POSIX file system; the first probe on a device forges its mtime and checks that `ctime` followed, and the verdict is kept per device in the cache file. Where it did follow (FAT/exFAT, some FUSE mounts such as sshfs) nothing on that device is cached and every file there is read, as on Windows, where PHP reports the creation time as `ctime`, and as for a file on any other device than the project's (a `vendor/` on another mount). A file is stable for a stamp when it has the same content after the run as when it was read, not merely the same `stat()`, so a file rewritten with the same bytes during the run no longer leaves its dependents unstamped. Template references persist in `<stateDir>/blade-references.json`, keyed by each template's content and the set of template paths. On the `plain` fixture a no-change `run` takes about 15–20 ms longer (median 0.178 → 0.196 s over 40 alternating runs).

  Content keys, fingerprint composition and the remote layout are unchanged; the graph file gains optional `n` per result and a top-level `configuration`, the object body optional `n`, `at`, `variants` and `aliases`, all of which older readers ignore.

  **Known, and not closed here:** the digest still looks at the graph's universe in three places, by what they mean: the `Sibling` rule, the Laravel fallbacks and the `static_declaration_edges` residue are presumptions about files nothing attributes yet, so when such a file gains its first edge the test files that carried it re-run once. Two publishers on the `file://` or HTTP backend writing the same object in the same instant can still drop one's variant (the last write wins): a miss for that machine, never a result served for another digest. On HTTP every publish of a digest an object does not hold costs one GET of the object before its PUT. That GET asks the current month's shard only: in the first run of a month, an object last written the month before is not found there, the publisher merges into its own mirrored copy (or starts a new object), and the copy written into the new month shadows the old one for readers, which look in the newest month first; variants the mirror never saw are then lost to them, which again is a miss. Stability is a comparison of content before and after the run, so a file changed during the run and changed back to the same bytes before it ended (A → B → A) counts as stable, and results that ran on B are stamped with A. That takes an edit made outside the suite while it runs and undone before it ends, or a test that rewrites a file another test reads and restores it (results that depend on test order); the window is the run itself, and the next edit to the file re-runs them. `record -- -c <file>` through the wrapper hands PHPUnit `-c` twice, as before this change (PHPUnit refuses it); the in-process extension honours `-c`.

## [0.11.0] — 2026-09-30

### Fixed

- **Fix: a branch's own cached passes overrode the failures of the baseline the run diffed from.** A graph holds one result layer per branch, each recorded at that branch's sha, and a run serves results from the branch's own layer laid over its nearest baseline's and the default branch's. The run decides what to execute by diffing against the ONE baseline it resolved, and nothing checked that a result served from another layer was valid for that diff. Reproduced: a feature branch edits `Money.php` and runs (its layer: passes recorded on that edit), reverts the edit and merges a `develop` that breaks `Money::add`. The merged tree is 0 files from `develop`, which wins, its diff is empty, and the feature layer's passes won over `develop`'s failures: `✓ 0 executed · 35 replayed`, exit 0, on a tree where plain PHPUnit fails 5 tests. The same happens when reverting a fix puts the tree back on the default branch's (the default branch wins, 0 files away), and when the branch's own layer has no sha at all because a CI pass saved its results without publishing a baseline.

  **Root cause: the diff vouches for one layer, and results were served from all of them.** The rule now enforced, by `Select\LayerAudit` before anything is served, in the wrapper and in-process alike: a result recorded in a layer at sha `s` may be served for a test file only if the rule chain would not select that file for the change set between `s` and the current tree. The layer whose sha is the diff base is trusted as its sha's tree — the run's own diff is exactly this rule applied to it. Every other layer the run would read from gets its own diff (one per audited layer; none at all in the common case, where the branch's own baseline is the one that won), and a layer whose sha is missing or that git does not have — a shallow clone — serves nothing: a miss, never a stale hit. An invalid entry of the branch's own layer is dropped, because the run is about to re-base that layer onto this tree and the next run would otherwise serve it again; another branch's layer is only masked for the run, since it is still valid on its own branch. The test is then served from the next valid layer, or executes. `--explain` / `--dry-run` say so: `tests/MoneyTest.php ← StaleLayer src/Money.php (feature@abc1234)`.

  **Falling back to a parent baseline's layer (`main` under `develop`) needs no check of its own when the run diffs from a baseline whose layer this machine holds — and was the same bug when it does not.** Below such a baseline, and on the premise the run already makes about it, no check is needed: that layer is a delta its own runs wrote, so a test it lacks is one its last complete run served from further down as valid on its tree, and the diff says nothing the test depends on has moved since. A lower layer that moved on can then only force a re-run, never hide one (pinned by a test where `main` breaks `Money::add` after `develop` was cut). But when the nearest baseline's sha was read off the remote, this machine has no layer for it, and the run served the default branch's results against a diff taken from somewhere else — `develop` breaks `Money::add` on one machine, a feature branch cut from it replays `main`'s passes on another. Those layers are now audited like any other.

  Two narrower holes of the same kind, closed with it. The last-run snapshot (which drops a dirty file already tested from the change set) now narrows a diff only when the run diffs from the branch's own baseline and the snapshot was taken at that baseline's sha (a CI run saves one without moving it): it describes the own layer, and a run serving from another branch's layer must not skip a file on its strength. And **`push` published cached results under content keys they were never recorded at**: it recomputes each test file's key from the working tree, so a stale layer result — or a pass recorded before an edit nobody had run yet — went to the shared cache as a verdict on content it never ran against. A result is now published only under the key it was recorded with — by `push` and by the push that follows every run, which after an incomplete run (one that never prunes the ids a test file no longer declares) published a renamed method's old result beside the new ones.

  **Not closed here, and known:** everything above trusts a layer's results as recorded on the tree at that layer's sha, and two situations break that premise. Results written into a layer without its sha moving — a CI run without `--allow-ci-baseline`, or an incomplete run — are served after the tree is reverted to that sha. Results recorded on a dirty working tree are served on another branch, or published with `remote_push: all` and adopted by another machine. Both happen on 0.10.2 too, and are tracked for a follow-up that stamps each result with the inputs it ran against. (Closed in [Unreleased]: every result is now served only while its content key and non-edge input digest match the tree, and a graph is published only from a clean working tree.)

  Content keys, fingerprints, the remote layout and the graph file format are unchanged: no cache is invalidated.

## [0.10.0] — 2026-09-11

- **New: `phpunit-replay remote:init` — sharing the cache stops being a document you read.** Every remote shape worked and every one of them needed a manual setup a user had to find, read and translate, which is where adoption dies. The command reads the project's `origin`, proposes a **private** cache repository beside it named `<project>-replay-cache` (from origin's repository name, never the working directory's), creates it through `gh` when `gh` is authenticated, publishes a probe object and reads it back **from a separate clone** to prove the round trip works, and writes `phpunit-replay.php`. `--dry-run` prints every action and takes none.

  Two things it does deliberately by not doing them. **It never touches a credential:** `gh` already owns the user's, and a test-tooling package that asks for a personal access token is a package nobody installs — without `gh` it prints the exact manual steps rather than failing, because someone who created the repository by hand still wants the rest. And **it never writes a secret into the project's repository:** publishing from CI needs a deploy key in the cache repository plus a matching secret in the project's own, which are two writes to real infrastructure, so it prints the steps and a workflow snippet and stops.

  It will not create a public repository and there is no flag to make it, because the cache stores test names, file paths and failure messages. An existing `phpunit-replay.php` is left byte-identical and the lines to add are printed instead — a config with `baseline_branches` already tuned must not be clobbered by a setup command. `--same-repo` configures the orphan-branch shape (`docs/DECISIONS.md` D-045) and prints the clone-size cost in its own output rather than leaving it in a document; it refuses a `--branch` that is the checked-out or default branch, since the probe would otherwise push a commit onto a code branch.

  `docs/sharing-the-cache.md` now opens on this command instead of on a six-option comparison table.

  **Known gap, pinned rather than closed:** `--name value` as two tokens is not recognised, only `--name=value`. `Console\Application`'s argv pre-splitter recognises a value-taking option only with its value attached by `=`, and the same already holds for `run --log-junit` and `prune --keep-months`; closing it changes shared argv behaviour and belongs in its own change.

- **Fix: a rejected remote push silently discarded every deletion the run had made, and then reported success.** `prune --remote` is the only caller that deletes, so it could print a count of objects it had not removed. Found while building `remote:init`, which needed to delete its own probe object and could not.

  All inside `Cache\Remote\GitRemoteCache`: `doEnd()` commits the deletion, the push is rejected by a concurrent client, and `adoptFetchedHistory()` does `git reset --hard FETCH_HEAD` — which discards the local commit *and* restores the deleted file exactly as upstream still holds it. The helper then replays `$buffer`, which holds `put()` bodies and knew nothing about deletions, so `commitStagedChanges()` found nothing staged and the retried push succeeded with `lastError` null. **Root cause: the reconciliation helper could replay a run's writes but had no representation of its deletions.** A second, narrower shape of the same cause: `put($k, …)` then `delete($k)` on one instance, where the buffer resurrected the object even after the reset.

  Fixed with a tombstone set beside the write buffer, and the cancellations in both directions are the part a naive fix gets wrong — `delete()` also drops any buffered `put()` of that key, `put()` also drops any tombstone for it, and `adoptFetchedHistory()` replays the buffer and then unlinks every tombstoned key. A `delete()` of a key absent from the local mirror tombstones too, deliberately: the mirror is only as fresh as its last `begin()`, so a key can be absent here and present upstream, and gating the tombstone on local presence would reintroduce the same bug through staleness instead of push timing.

  Nothing was ever corrupted — this is garbage collection, and a later run retried — but it was silent, which is what the retry loop exists to prevent.

## [0.9.0] — 2026-09-11

A shared cache could serve a result recorded under a different PHP minor or a different OS, and every developer's local read-through mirror grew without bound because nothing ever collected it. Both are closed by the same change, and the design record is `docs/proposals/remote-layout.md`.

**Remote objects recorded before this release become unaddressable.** Graphs are not invalidated — `structuralMatches()` is unchanged, so edges and local results survive and keep replaying — but every content key moves, so a machine will not find the previous generation's objects on a remote and will re-record what it needs. The first `prune` after upgrading truncates that generation out of the local mirror.

- **A result's address now carries the part of the environment that can change its outcome.** `Cache\ContentKey` folded only `Fingerprint::canonicalStructural()` into its material, so the environmental half of the fingerprint was excluded from the address — and `RunPipeline::replayFromRemote()` re-checks nothing beyond the key, the object's existence, and whether it holds a status that must be re-run. A result recorded under PHP 8.2 was therefore findable and replayable by a machine on PHP 8.4. Local recordings were never at risk, because environmental drift discards a machine's own results; that protection simply did not extend to what arrives from a remote.

  The new `Fingerprint::canonicalResultEnvironment()` covers `php` (`MAJOR.MINOR`) and `os`, and is deliberately **not** the environmental bucket verbatim. `driver` stays out because a coverage driver changes which lines are *reported*, not whether an assertion passed — and this package's own scripts alternate them (`composer test` is pcov, `composer test:xdebug`), so including it would halve a developer's hit rate daily for no correctness. `coverage` stays out because a remote object carries no coverage snapshot at all; snapshots are local, at `<stateDir>/coverage/<k>.cov`, and are keyed by the test file's own content hash rather than by a content key.

  `php` and `os` remain in the environmental bucket as well, and that redundancy is load-bearing: a graph adopted from another environment still matches structurally, so its **edges** are inherited — correctly, since edges are a property of the tree — while its **results** carry addresses this machine will never compute. `environmentalDrift()` → `clearResults()` is the only thing that removes them.

  This was chosen over scoping the remote object tree by a generation and environment path, which an earlier proposal had recommended. Putting the environment in the address rather than the path is what makes the next item a proof instead of an estimate.

- **`prune` now collects the local read-through mirror, which nothing had ever collected.** Everything read from a remote is mirrored at `<stateDir>/remote/cache/objects/<k>.json`, flat; `--keep-months` existed only on `prune --remote`, which garbage-collects the *remote*. Measured on one populated mirror after a single `composer.lock` change: **726 of 1,452 objects unreachable** — exactly one dead generation, on every developer machine, with no way to remove it. `prune --remote` had always collected the remote by reachability and had simply never applied that rule to its own mirror.

  With the environment in the address, every object a machine can address is by construction from its own environment, so an object recorded elsewhere is *provably* unreachable rather than merely absent from today's graph.

  **Eviction is a truncate, not an unlink**, and needs no change to either code path that reads the mirror. The file does two jobs and each inspects a different part of it: `putObject()` tests `is_file()` for its "already published" marker, and `object()` decodes the contents. A zero-byte file keeps the marker true and fails the decode, so the blocks are freed, nothing is re-published, and the next lookup refetches and refills. `prune --forget-published` unlinks instead, reclaiming the inode at the cost of a redundant `put` — idempotent, because objects are content-addressed and immutable — and is behind a flag because on a client with `remote_push: objects` that re-publication is noise on a shared remote.

- **`prune` also collects `<stateDir>/coverage/`, by a different rule.** Snapshots are keyed by `ContentHash::of()` of the test file itself, not by a content key — a content key additionally needs a `Graph`, which does not exist inside the PHPUnit child process in filtered mode. So a snapshot is live iff its key is the current on-disk content hash of a test file the graph still knows; anything else is stale because the file changed or is gone, and in both cases its key can never be computed again. Nothing had collected these either.

- **`status` reports the mirror**: `mirror: 1452 objects · 726 reachable · 2.4 MB reclaimable`. Answering "how much of this is dead?" previously required reconstructing every baseline's keys by hand.

- **Documentation: `DECISIONS.md` is back, and two things the docs claimed the code no longer did.** The decisions log had been deleted wholesale — 216 lines, 43 entries — for a single line naming a vendor namespace from an early spec draft, while seven places in `src/` went on citing it at a path that did not exist. Restored at `docs/DECISIONS.md`, that line reworded, all seven citations repointed, and two new entries: why the environment went into a result's address rather than into a deeper object path, and why the cache *may* live on an orphan branch of the project's own repository while a dedicated repository stays the recommendation. `docs/INTERNALS.md` said a rejected remote push reconciles with `fetch` + `rebase`; `GitRemoteCache` never rebases, and its docblock explains why — a `--depth 1` fetch severs the parent link, so two mirrors that really are descendants of one history can look unrelated to `git rebase`. It also documented every `prune` flag and neither collection sweep this release adds.

- **Documentation: `docs/sharing-the-cache.md` leads with what to do.** It opened on a seven-by-seven comparison of six options, asking a reader who does not yet know what any of them are to choose between all of them. A **Start here** section now gives the recommendation and its four steps, the table is a reference near the end, and the guide says at the point the repository is created why it must be private (the cache stores test names, file paths and failure messages) and why the config uses HTTPS for people and SSH for CI.

## [0.8.0] — 2026-09-10

Two correctness fixes, both found by installing the package in a second real project whose
`phpunit.xml` and test-class layout differ from the first one it was developed against. Neither
could have surfaced on a project without group exclusions or without abstract base test classes.

**This release invalidates every existing graph once.** `Cache\Fingerprint` gains a new
unconditional structural key, `edges_by_running_class`, because the second fix changes which file
an edge is recorded under — so a graph recorded before it is contaminated by definition.
`phpunit-replay status` names the key in its drift report rather than discarding the cache
silently. Nothing else changed: no configuration key was added, renamed or given a new default.

Measured on a real 4,820-test Laravel suite before and after, same tree, same database, only the
package version differing: a `run` with nothing changed went from **4m10s to 0.57s** —
`0 executed · 4820 replayed`. Before the second fix the package saved no wall clock at all on
that suite (4m10s against a 4m27s baseline), because the two most expensive test files in it were
permanently outside the cache.



- **Fix: a test method inherited from an abstract base class recorded no edges at all, permanently, on the concrete class that actually ran it.** Reproduced on a real 4820-test Laravel suite: two `final` test classes extending a shared abstract base, adding no test methods of their own — the base declares them and is never itself run by PHPUnit (abstract classes cannot be instantiated). `baselines['<branch>']['results']` correctly held both classes' results, keyed by test id, but `edges` did not: the abstract base had 841 recorded dependencies and the two concrete classes had none. Consequence: the two concrete files were permanently "unknown test files" and re-ran on every pass — the two most expensive files in the suite, measured at 466s under pcov, on a replay pass that should have taken seconds.

  **Root cause:** four call sites — `PHPUnit\Subscribers\StartRecordingOnPreparationStarted`, `CollectResultOnPreparationStarted`, the class-level branch of `RecordNotCacheableOnPreparationStarted`, and `Laravel\Subscribers\ArmLaravelTrackersOnPrepared` — used `PHPUnit\Event\Code\TestMethod::file()` to decide which file a test's edges/result/not-cacheable-marker/database-table-widening counts against. `file()` resolves through native PHP reflection on the method, which for an inherited method returns the file of the class that DECLARES the method body — never the class actually running it. `TestMethod::className()`, by contrast, is always the concrete, running class, regardless of where its methods are declared.

  **The fix:** a new `PHPUnit\TestMethodFile::of(TestMethod $test): string` reflects `className()` and returns its file, falling back to `file()` only when that class cannot be reflected (does not happen in ordinary operation — a `TestMethod` is only ever built from an already-instantiated test object). All four call sites now go through it; a fifth and sixth `$test->file()`-adjacent computation elsewhere in the codebase were already correct or already file-independent and needed no change. Neither a `#[DataProvider]` dataset nor a `#[Depends]` relationship changes which class is running, so both are unaffected — checked with an actual data-provider-driven inherited method, not just read from PHPUnit's source.

  **A second guard — refusing to key `edges` by an abstract class's file at record time — was considered and found unnecessary.** With the fix above, every call site that could create a key in `edges` resolves through `className()`, and PHPUnit never instantiates a test whose class is abstract, so the abstract base cannot become a key on any path; confirmed empirically, not just reasoned about. What DOES matter, and falls out of the fix with no extra code: the abstract base is source the concrete tests depend on (its method bodies are the lines that execute), so it must appear INSIDE the concrete files' own dependency lists — editing it still selects both concrete tests.

  **Every existing graph is invalidated once.** A graph recorded before this fix has an inherited test method's edges under a file that is not even a test file this package selects — `Cache\Fingerprint::compute()` gains a new, unconditional structural key, `edges_by_running_class` (always `true`, alongside `edges_exclude_ignored`), rather than a bare `SCHEMA_VERSION` bump, for the same reason that key was added on: a schema-only bump can never be *named* in a drift report, so the user would see every graph discarded with nothing explaining why. `phpunit-replay status` names it (`edges_by_running_class (drift)`).

  Two variants of the reproduction are covered, because they are not equivalent: an abstract base named with the configured test suffix (which additionally makes PHPUnit's own discovery warn "declared ... is abstract" — a separate, pre-existing concern this package does not attempt to fix) and one named without it (the natural remedy for that warning, and the more common way an unrelated project would write a shared test base). The file-attribution defect survives the rename undiminished. Full detail in `docs/INTERNALS.md`, "Abstract-base test classes attribute their edges to the wrong file".

- **Fix: a project whose `phpunit.xml` excludes a group (a common way to quarantine tests that hit a real, paid third-party API) was silently inert — and the false-green vector that made this worse.** `PHPUnit\ConfigurationReader::hasPartialSelection()` read `hasFilter()`/`hasGroups()`/`hasExcludeGroups()`/`includeTestSuites()`/`excludeTestSuites()` off PHPUnit's own *merged* `Configuration` — XML plus CLI — and `Configuration\Merger` folds a project's XML `<groups><include>/<exclude>` and `defaultTestSuite` into that merged object whenever the CLI side is silent on them. So a project whose `phpunit.xml` declares `<groups><exclude>` (reproduced on a real 490-test-file project with four such opt-in groups) reported a partial selection with **zero command-line arguments**: `record` (bare, no arguments at all) refused outright ("does not accept a partial PHPUnit selection"), degraded to a plain sequential PHPUnit run of the whole suite, and exited non-zero; `run` (bare) never recorded a single edge, on every ordinary invocation, so its graph could never be built. The package was silently inert on such a project from the first command.

  **A second, worse consequence surfaced while diagnosing it.** On what `hasPartialSelection()` (wrongly) saw as a partial selection, `Console\Runner\RunPipeline` set `recordsEdges: false` and `complete: false` but still called `Cache\GraphUpdater::apply(...)` — and `apply()` gates only edge *writing* with that flag; it merges *results* regardless, for any test file the graph already knows about (a common shape: an opt-in group tagging individual methods inside test classes that otherwise participate normally in the recorded suite, so the FILE is already known even though the specific, excluded test id never was). So `phpunit-replay run --group live-ai` on such a project cached the real result of tests that call a real, paid third-party API, and a later ordinary run could replay that cached result instead of calling the API again — a false-green vector, and the more serious of the two defects, since it was not the reported symptom.

  **The fix has two parts.** (1) `ConfigurationReader` now answers `hasPartialSelection()` from the CLI half of the configuration alone (`PHPUnit\TextUI\CliArguments\Configuration`, built separately by `Console\Runner\ProjectLocator::buildConfiguration()` for the wrapper, and reconstructed from the real `$_SERVER['argv']` for the one caller with no wrapper in front of it, `PHPUnit\ReplayState::bootInProcess()`, via the new `ConfigurationReader::cliConfigurationFromArgv()`) — XML-declared group/testsuite configuration is the project's own definition of what "the whole suite" means, never a selection. Uncertainty (argv unavailable or unparseable) fails closed, as if a selection were present, never open. (2) A CLI selection — `--filter`/`--exclude-filter`/`--group`/`--exclude-group`/`--testsuite`/`--exclude-testsuite`/an explicit path — now persists **nothing at all**: no edges, no results, no baseline, no pruning, no quarantine write, no remote publish, in both `RunPipeline` (`run`'s `runResultsOnly()`, and `verify`, which had the identical `apply()`-called-regardless pattern) and in-process (`ReplayState::persistInProcess()`). Not "edges off, results on" as before: a CLI selection means "run exactly this," and nothing observed under it enters the cache. The user's own selection still runs, for real, exactly as before — only what gets written changed.

## [0.7.0] — 2026-09-09

The package's generic namespaces no longer contain framework-specific code. Nothing in this
release changes behaviour, no configuration key changed, and no cached graph or remote object is
invalidated by it.

- **New: `docs/proposals/remote-layout.md` — a design proposal, not an implementation.** Scoping the remote object store by generation and environment (`objects/<generation>/<environment>/<yyyy-mm>/<k>.json`), written down before any code because it changes the on-disk layout and that is cheap to change exactly once. It closes the one way a shared cache can currently serve a wrong result — a content key is built from the structural fingerprint only (`ContentKey.php:46`), so `php`/`driver`/`os`/`coverage` are not part of a result's address, and `RunPipeline::replayFromRemote()` adopts an object on a key match without re-checking them — by making a cross-environment read *unreachable* rather than merely checked. It also turns dead-generation purge from a full object scan into a directory delete: measured on a real cache repository, one `composer.lock` change left 1,452 objects of which 726 were reachable, and every dependency bump adds another full generation. The graph deliberately does not move, because the package already draws the line the layout would reflect: `structuralDrift()` makes a graph unusable while `environmentalDrift()` keeps its edges and discards its results. - **Data-loss fix: a transient remote-cache push failure silently dropped that batch of test-result objects from the shared cache forever, with no error on any later run.** Reproduced today against a real private GitHub repository. `Cache\Remote\ObjectStore::putObject()` wrote its local "already published" marker (`<stateDir>/remote/cache/objects/<k>.json`) as soon as `RemoteCache::put()` returned `true` — but `true` means "durably stored" only for the `file://` and HTTP backends; for the git backend (`GitRemoteCache::put()`) it only means the object was staged into the local mirror's working tree. The actual push happens later, in `end()` (`RemoteCache::end()` → `GitRemoteCache::doEnd()`), which returns `void` and reports failure only through `lastError()` (surfaced by `RunPipeline::closeRemote()`/`warnRemote()`). So the marker got written on a promise `end()` had not kept yet, and `putObject()`'s own skip check (`is_file($local)` ⇒ "skip (already published)") then refused to ever retry that key again, on any later run — forever.

  Observed, in this order (the ordering is part of the defect): (1) a first `push --graph` over an SSH URL failed because the SSH agent could not sign — the output read `pushed 726 object(s) to the git remote`, then `pushed the <branch> baseline (graph/p-.../<branch>.json)`, and only then `remote (git): git push rejected and fetch failed: exit 127` — success printed twice, the failure reported third. (2) Retrying over HTTPS (working credentials) reported `pushed 0 object(s)` and pushed only the graph: the remote ended up with `graph/` and zero objects, while the local mirror's git log showed `replay: +1 objects` and `<stateDir>/remote/cache/objects/` already held all 726 marker files left over from step 1. (3) Deleting `<stateDir>/remote/cache` and retrying pushed all 726 objects for real, confirming the markers — not the remote — were the source of "already published". In production this means one transient network or credential failure during a push silently drops that batch of objects from the shared cache forever; a team's cache stays half-populated and nobody can tell why.

  **The fix**: `ObjectStore` now buffers what `putObject()` hands to `put()` this session (`k => body`) instead of marking it published immediately. A new `ObjectStore::confirmPublished(): int` writes the buffered markers — and only that method may — and is itself a no-op (writes nothing, returns 0) whenever `RemoteCache::lastError() !== null`, so a caller cannot turn a failed push into permanent data loss even by forgetting the check. `RunPipeline::closeRemote()`, `PHPUnit\ReplayState::closeRemote()` (the in-process/Paratest-worker path — it duplicates `RunPipeline`'s push logic and carried the identical bug) and `PushCommand` all call it right after `end()`. **The failure direction is deliberately asymmetric, stated in `confirmPublished()`'s own docblock**: a *missing* marker costs one redundant `put` of a content-addressed key on the next run — a documented no-op (`docs/sharing-the-cache.md`: "two machines writing the same key at the same time is a no-op, never a conflict"). A *premature* marker costs that object forever. When in doubt, the marker is not written.

  **Reporting fixed too**: `PushCommand`'s `pushed N object(s) to the … remote` and `pushed the <branch> baseline (…)` lines used to print before `end()` ran (see step 1 above) and, on the git backend, could claim objects that never landed (step 2). Both now print only after `end()` confirms no error, and the object count comes from `confirmPublished()`'s own return value — what actually got a marker, not what was merely staged. The same premature count existed at debug level (`PHPUNIT_REPLAY_DEBUG=1`) in `run`/`record`'s own auto-push (`RunPipeline::pushAfterRun()` and its `ReplayState` mirror); it is now reported from `closeRemote()` in both, after the same confirmation.

  **Checked for the same pattern elsewhere** (a local file recording remote state on the strength of a `put()`/`delete()` return, without waiting for `end()`): the branch-baseline publish path (`graph/<projectKey>/<branch>.json`, `ObjectStore::putGraph()`) keeps no local copy at all, so there was nothing to fix there beyond the same premature-print issue `PushCommand` already had. `PruneCommand --remote`'s deletions (`RemoteCache::delete()`) are staged the same way on the git backend, but nothing reads a local "already deleted" marker to decide whether to skip a future delete, so a failed push after a prune cannot silently and permanently hide an object the way a failed push after a `put` could — worth documenting, not fixing. `RemoteCache`'s interface docblock now says so explicitly: `put()`/`delete()` returning `true` means "accepted", not "durable".

  `tests/Unit/Cache/Remote/ObjectStoreTest.php` pins all three shapes against a new `Tests\Support\FakeRemoteCache` (`put()` always succeeds; `end()`/`lastError()` independently controllable — the one thing no real backend lets a test do directly): `testAFailedEndWritesNoMarkerAndTheNextRunRetriesThePut` is the regression that matters, `testASuccessfulEndConfirmsTheMarkerAndTheNextRunSkips` is the happy path, and `testACrashBeforeConfirmPublishedDegradesToARedundantPutNeverASkip` pins the crash-between-a-successful-push-and-the-marker case to a redundant put, never a wrongful skip.

If a path should never be an edge, put it in `.gitignore`.

- **Correctness fix: a Laravel migration, seeder or console command could hold a coverage-derived edge that many real dependents shared but only ever one of them was credited with — and editing the file then re-ran only that one.** The property that actually decides this, and the wrong one to check: not "two parallel passes agree" but **serial vs. parallel**, the two extremes of first-loader attribution. Serial (one process for the whole suite) makes a once-per-process body execute exactly once in the entire run, crediting the minimum possible — one test; 8-worker parallel executes it once per worker, crediting up to eight; full process isolation would credit every test that triggers it. Measured directly on a real 9,056-test Laravel project, both with `static_declaration_edges` on and with it off: a serial `record` produces 60,282 edges, an 8-worker parallel one 60,572 (**+290**), and **95 of 726 test files have a different dependency set between the two shapes** — two parallel passes agreeing (already pinned for the declaration/first-loader case) proves far less than it looks, because serial is reproducible precisely by making one deterministic arbitrary choice every time. That is a real false green, not merely a residual: if a 130th test genuinely depends on such a file, editing it re-runs nothing for that test.

The file keeps no `fileId`, landing it in `Select\ResiduePatterns`' existing no-`fileId` bucket, so a change to it now selects **every test the graph knows** via `Select\Rules\WatchRule` instead of whichever one test a worker happened to credit. Same cost in expectation (19% of test files always running either way), but it does not produce a unique graph — the disputed edges stay recorded, so content keys keep moving between machines and the remote cache stays exactly as unshareable as before. Refusing the edge changes what the graph *is*; exempting the tests would only have changed which ones run, at the same price, leaving the actual non-determinism in place.

So **every content key matched**, and the 14–22 residual measured under 8 workers is Paratest's distribution rather than anything in this package's logic or in the suite. That is what makes the single-producer approach viable: a graph recorded once in one shape and distributed with `push --graph`/`pull` gives every machine the same object addresses by construction, without waiting for convergence.

## [0.4.0] — 2026-09-09

- **`verify`'s `would replay` figure was measured in a way that could not answer the question the README told people to act on — the old wording promised something the old code could not deliver.** The README presented it as the figure to watch when deciding whether the fast `run` lane can serve as a per-PR merge gate: how much of the suite that lane would cover. It was measured by comparing each **stored** content key against one **freshly re-observed** on the same pass (`RunPipeline::verify()`'s `$wouldReplay` loop skipped a test whenever `$oldKey !== $newKey`). But `verify` re-records edges, and `Graph::unionEdges()` only ever grows a test file's dependency set, so any test that gained an edge on that very pass got a new key and dropped out of the count. What the figure answered was *"is this test's dependency set byte-identical to the last recording?"* — a question about the graph's convergence, not about the fast lane. It therefore depended on how many passes had run rather than on the tree: on a real 9056-test suite `9056 − would replay` fell 2001 → 1941 → 1502 → 1253 across four identical full passes (and 1135 → 1032 on the 0.3 line with `static_declaration_edges` on, from a fresh graph), monotonically shrinking and never converging, while `run` on the same unchanged tree replayed 9056 of 9056 — because `run` never re-observes anything, it reads the stored keys. It was wrong in the opposite direction too, on a change that moves no key at all: creating a watched-but-uncovered file (a `.env` matches a default watch pattern) puts every test file in the run list, so a `run` there replays nothing, yet the key comparison happily reported the whole suite as "would replay". This is the third and last defect in that loop; the two earlier ones (iterating the whole cached corpus, and `verify --filter` rewriting the graph, both fixed above) were arithmetic — this one was the measurement design.
  It is now decided the way `run` decides it, by the same code. New `Select\ReplaySet` reads the run list `Select\RunListBuilder` produces and counts every cached result whose test file is **not** in it and still exists on disk. Run-list absence is almost the whole rule, because the run list already holds the affected selection plus the unknown/rerun/quarantined/not-cacheable buckets, so a surviving file is exactly one `ReplayState::decideFresh()` reaches its cached-result branch for. The disk check covers the single exception — a *deleted* test file, which is in no bucket either (they are all built from a directory walk or an `is_file()` check) and so was absent from the run list for the one reason that does not mean "replayable". `run` had always masked that by pruning before building its list (deleting a test file is itself a change, so `pruneResultsForMissingFiles()` runs), so this incidentally removes a latent over-count from `run`'s own replayed figure for any pass that reaches the list unpruned. `RunPipeline::replayedAgainst()` — the figure `run` and `run --dry-run` report as replayed — now reads that same class, so the two numbers cannot drift apart. Content keys play no part in the decision, matching `decideFresh()`, which reads a cached result straight out of the graph and never compares a key (the key addresses the *remote* object store). The decision is computed **before** the PHPUnit child is launched rather than reconstructed afterwards: `apply()` rewrites the graph's edges, keys and results in place, and the run list comes from a git diff plus a directory walk, which after the run would read a working tree the suite (and the generated `.phpunit-replay.xml`) had already changed. A partial CLI selection no longer collapses the figure to 0 either — it narrows which tests the figure is reported over, not the run list it is decided against. `would replay` is now a property of the tree, so two `verify` passes over an unchanged tree report the same number by construction rather than by luck; `tests/Integration/VerifyWouldReplayMatchesTheRunListTest.php` pins that against a new fixture (`tests/Fixtures/Projects/keydrift`) whose observed dependency set grows between passes, and which reported `2 would replay` then `4 would replay` from identical inputs before this fix.
- **New `unverified` figure on `verify`'s summary line**, so that the population divergence detection silently exempts is stated instead of absorbed: `Verify  ✓ 1240 tests · 1198 would replay · 0 divergences · 0 unverified (lifetime: 2 in 143 runs)`. Divergence detection itself is deliberately unchanged — it still compares only results whose stored and re-observed keys match, which is the trustworthy half of the line (0 across six passes on that 9056-test suite) and errs the safe way, since it also checks tests `run` would have re-executed anyway and so can only over-report a divergence, never miss one. What it cannot check is a test whose key moved. `run` would still have served that test's cached result, so it is precisely the part of `would replay` a pass is not vouching for — and it used to disappear into the old count rather than be reported. `unverified` counts it. It settles to 0 as the graph's edges stop moving, and never affects the `✓`/`✗` symbol or the exit code. Noted for a future release and deliberately not changed here: because `run`'s local replay path never compares keys at all, the key-equality gate on divergence detection has no counterpart in the behaviour it models, and dropping it would let `verify` check the cached result of every test that would be replayed — at the cost of moving the divergence number, the one figure on that line currently known to be trustworthy.

## [0.3.0] — 2026-09-08

- Added `static_declaration_edges` (opt-in, **default off**): a second source of dependency edges, derived from static name references rather than from coverage. A coverage driver can only attribute a file it saw execute, and PHP runs a file's top level once per process, so a declaration — an enum's cases, a constants class, an interface, a `return [...]` config — is credited to whichever test in that process loaded it first, and to no other. Measured on a real 9056-test suite, one enum was credited to 8 tests of which only 2 mentioned it, while 21 test files referenced it directly: editing it re-ran none of the other 19. `Graph::unionEdges()` (above) stops such an attribution from being *lost*; it cannot create one that never existed. This adds the missing half. A php-parser pass classifies every source file and records its function-body line ranges, cached under `<stateDir>/analysis/v<RULES_VERSION>/`; a coverage edge then counts only when executed lines fall **inside** a body, which is order-independent because every caller runs those lines every time; and a file that declares a name becomes a dependency of the tests that name it. What neither mechanism reaches — `config/`, `lang/`, a file declaring nothing, a file php-parser cannot read — keeps the conservative residue fallback rather than being dropped, since dropping it is the very false green this exists to prevent.
  The hop is deliberately asymmetric, because indexing every declaring file symmetrically cost **+105.54%** edges on that suite (62,743 → 128,962), 60% of it from five files that merely *register* classes and are behavioural dependencies of 700 of 726 tests: a target with no body gets the full hop (test file plus its behavioural dependencies), since coverage can never attribute it; a target with bodies is reachable only from a test's own source, since every caller already gives it a behavioural edge. Measured cost of the shipped form: **+2.84%** (1,781 edges), median dependencies per test 82 → 84, and those five files contribute exactly zero. Classification costs 3.4s cold and 0.26s warm on 2,195 files.
  The flag and `DeclarationScanner::RULES_VERSION` both participate in the **structural** fingerprint, but only while the flag is on: turning it on or bumping the rules changes what an edge *means*, so it discards the graph deliberately rather than silently mixing two edge semantics, and `status` names which of the two drifted. Projects that never opt in are untouched — with the flag off the suite is byte-identical to the previous release.
  Known limitation, documented at `Recorder::filesWithExecutedLines()`: `XdebugDriver` starts coverage without `XDEBUG_CC_UNUSED`, so xdebug never reports an unexecuted line and the inherited Pest exclusion cannot fire under it, meaning the body filter removes more edges under xdebug than under pcov. Because edges are unioned, a mixed pcov/xdebug CI matrix converges on the union of what the two attribute, never the intersection.

## [0.2.0] — 2026-09-08

- Fixed: correctness — re-recording a subset of tests (`run`, `verify`, in-process replay) could silently drop a test's dependency edge instead of keeping it. A coverage driver attributes a file's declaration footprint (class/enum/const, or any top-level statement) to whichever test happened to load it first in that process, so a partial re-record whose attribution differed from a previous, complete one could make a test's content key stop including a file it still genuinely depends on — a false green: editing that file no longer changed the key, so the stale cached result kept being replayed instead of the test ever running again. `GraphUpdater::apply()` now unions a re-record's edges into the graph (`Graph::unionEdges()`) instead of replacing them (`Graph::replaceEdges()`, still used to seed/replace a graph's state directly); a genuinely stale edge is shed by the next full, fresh `record`, which always starts from an empty graph. Laravel's per-test table tracking (`replaceTestTables`) is unaffected — it comes from a live query listener re-attributed on every run, not a load-once coverage artifact.
- Added `prune --stale-edges`: now that edges only ever accumulate (previous entry), a dependency a test genuinely stopped needing had no way to leave the graph short of a full, fresh `record` — on a large suite the expensive operation people avoid — and lingered forever, changing the test's content key (and forcing an unneeded re-run) every time that unrelated file changed. `--stale-edges` (`Graph::pruneMissingDependencies()`) drops a single dependency edge, inside a test file that still exists, when the dependency's own file is confirmed gone from disk — the one staleness signal that cannot misfire regardless of run order or which test a coverage driver's first-loader-wins attribution happened to credit: "not observed by a recording pass" is never treated as evidence of staleness (`Graph::unionEdges()`'s docblock explains why that would be unsound — same reasoning, mirrored), only "the file itself does not exist" is, so a live dependency can never be removed by this. Deliberately opt-in rather than folded into the no-flag default (`pruneMissingTestFiles()` + `--branches`): those prune purely historical state with no bearing on cache validity, while a dependency edge is exactly what a changed file is matched against to decide whether a cached result can still be trusted, so trimming one — even by a rule this narrow — stays behind an explicit flag the user opts into, same as `--flaky`.

Code written against the old shape doesn't error against the new one — it just finds no strings to match and concludes nothing executed. Before this fix that meant every `--coverage-*` run under cc 14.3 silently recorded an empty dependency graph (TIA would conclude nothing depends on any source file) and an empty coverage snapshot, with no exception and no warning anywhere. - `record` now exits `2` when it degrades to a plain PHPUnit run and that run itself reported success (exit `0`): a degrade never writes a graph or even the state directory, so forwarding PHPUnit's own "0" straight through made a `record` that recorded nothing indistinguishable from one that succeeded (reported: a removed PHPUnit method degraded a CI `record` step, which then ran all 9056 tests, printed a normal summary, and exited 0 with nothing on disk — noticed only by manually checking for the state directory). `run` is unaffected: its exit code is still PHPUnit's own regardless of whether it degrades, per the documented "never change PHPUnit's exit code" guarantee, since unlike `record`, `run`'s exit code is the actual pass/fail signal CI gates on.
- **Data-integrity fix, and a hole in the guarantee directly above**: `record` carrying a partial CLI selection (`--filter`/`--exclude-filter`/`--group`/`--exclude-group`/`--testsuite`/`--exclude-testsuite`/an explicit path) silently took the results-only branch meant for `run` — `RunPipeline::run()` (the entry point `record` shares with `run`; `RecordCommand` just sets `RunRequest::$record = true`) checked `ConfigurationReader::hasPartialSelection()` before ever looking at `$request->record`. That branch writes no edges, publishes no baseline, and prints no warning, so `record -- --filter=X` executed and returned PHPUnit's own exit code with nothing recorded — the same silent-loss-of-the-whole-feature failure class as the two fixes above, and specifically unreachable by the `record`-degrade exit code immediately above it, since results-only mode is a deliberate destination for `run`, not a degrade. A partial run cannot produce the one thing `record` exists to produce — pruning and the published baseline sha both assume the whole suite ran — so `RunPipeline::resolveEnvironment()` now refuses this combination outright, before the graph is even loaded, by degrading exactly like every other reason it cannot proceed: the user's selection still runs for real via the plain, unwrapped PHPUnit fallback (the run is never silently skipped), the graph is left completely untouched, and the existing "degraded `record`" rule above turns a passing fallback into exit `2` instead of a false `0`. `run`/`verify` are unaffected — only `$request->record` reaches the new check — and keep handling a partial selection exactly as before (`runResultsOnly()`, `verify()`'s own `hasPartialSelection()` gate). Also checked, and found unnecessary: `runResultsOnly()` has no missing-coverage-driver check the way `runRecord()`/`verify()` do, because it never needs one — it always runs with `$iniFlags = []` and always calls `GraphUpdater::apply(..., recordsEdges: false, ...)`, so no coverage data is ever collected or required; adding one would only break `run --filter` on driver-less machines (SPEC §16 acceptance criterion 7) for no correctness gain.
- **Visibility fix, in-process mode's equivalent of the gap directly above**: a project configured with the standing `mode: record` (SPEC.md §6.1) also silently lost its baseline refresh whenever a developer ran `phpunit --filter=X` directly (no wrapper) — `ReplayState::decideMode()` checks `hasPartialSelection()` before `config->mode === 'record'`, downgrading to `Mode::ResultsOnly` with nothing said. Unlike the wrapper's own `record` command, refusing outright is the wrong fix here: `mode: record` is a standing configuration, not a one-shot imperative, and a developer running a filtered suite mid-session is doing an entirely ordinary thing — downgrading to results-only is the *correct* behaviour, it is what stops a filtered run from silently writing a partial baseline. What was missing was only that nothing said so. Considered and rejected: an unconditional `Warnings::warn()` on every such run (in a `mode: record` project this could fire on most filtered runs during normal development — a warning people learn to ignore is worse than none) and a `Warnings::debug()`-gated one (invisible unless `PHPUNIT_REPLAY_DEBUG=1` is already set, so it never reaches someone who doesn't yet know to look for it — the exact person confused about why their baseline never refreshes). Instead: the summary line the extension already prints unconditionally once per in-process run (`ReplayState::summaryLine()` → `Report\Summary::format()`) now gains a `record mode: baseline NOT refreshed (partial selection)` segment when `decideMode()` recorded that a standing `mode: record` — not just `auto`'s ordinary "no baseline yet" — was what the selection defeated (`ReplayState::$recordModeDowngraded`, `Summary::$recordModeDowngraded`). This costs no new noise channel: the line was always going to print. The wrapper's `run --filter` (and `run`'s own `mode: auto` first-run bootstrap) are both completely unaffected and stay exactly as silent as before.
