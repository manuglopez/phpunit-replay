# Changelog

All notable changes to this project will be documented in this file.

## [Unreleased]

- **Correctness fix: an edge could point at a file `git` ignores, and on a Laravel project that made a test's dependency set — and therefore its content key — depend on which paratest worker happened to run it.** Two `record --parallel=8` passes on a real 9056-test Laravel project, identical working tree, each from an empty graph, produced two different dependency graphs: only 537 of 726 tests' dependency sets matched between the passes, 189 differed, and 421 distinct files moved from one pass to the other. 281 of the 2115 recorded "source files" were `bootstrap/cache/views/test_<N>/<hash>.blade.php` — Laravel's compiled Blade view cache, written into a **per-paratest-worker-token directory** (Laravel Parallel Testing rewrites `view.compiled` per worker). `git check-ignore` confirmed every one of those 281 paths is ignored; zero tracked files were among them. The root cause: `Laravel\BladeTracker` links `$view->getPath()` for every rendered view unconditionally, and for an ordinary template that path is the real source `.blade.php` — correct — but for `Blade::render($string)` and inline/anonymous components, Laravel gives the SAME view object a path that is instead its own disposable compiled artifact (`Illuminate\View\Component::createBladeViewFromString()` writes the raw string into `config('view.compiled')` itself, content-hashed, under the `__components::` namespace). Livewire-heavy apps hit this constantly. Because such a file can never appear in `Change\ChangedFiles::since()` (an ignored path never shows up in `git status`), the edge was pure content-key pollution that could never trigger a rerun — it could only make two otherwise-identical recording passes disagree.
  Fixed in two layers. **The producer**: `Laravel\BladeTracker::arm()` now refuses to link a view path that lies inside the application's compiled-view directory, read fresh from the live `config('view.compiled')` **inside the composer closure**, never cached at `arm()` time — Laravel Parallel Testing rewrites that config value per worker process, after `arm()`'s once-per-Container bootstrap has already run, so a value captured once could be stale for the worker actually rendering a given view. A belt-and-braces fallback (`Record\SourceScope::isNestedNoisePath()`, a new small accessor onto the same fixed directory list `SourceScope` already excludes coverage from — chosen over threading a full `SourceScope` instance into the tracker, since the tracker needs only that one narrow check and threading an instance would have coupled it, and every caller between the extension bootstrap and `ArmLaravelTrackersOnPrepared`, to `PHPUnit\TextUI\Configuration\Registry`) refuses `bootstrap/cache`/`storage/framework`/`storage/logs` even when `config('view.compiled')` itself cannot be read. `Record\Recorder::linkSource()` itself is deliberately untouched — its principle ("explicit links never went through coverage, so they are not the recorder's to second-guess") still holds for a real template; `tests/Unit/Record/RecorderBehaviouralEdgesTest.php` now states both halves explicitly.
  **The net**: even with the producer fixed, `Cache\GraphUpdater::apply()` and `Analysis\StaticEdges::expand()` — the only two places an edge is ever written into the graph — now refuse any edge whose source `git check-ignore` matches, batched once per `apply()` call over stdin (never once per file: a 9056-test suite has tens of thousands of edges). This is deliberately **IGNORED, not UNTRACKED**: an ignored file can never appear in a git diff, so an edge to one is pure pollution that can never trigger a rerun — but an untracked-but-not-ignored file (a brand-new source file nobody has `git add`ed yet) **does** appear in that diff and must keep its edge, or `Select\Rules\PhpEdgeRule` would silently stop selecting the test that depends on it until the next full fresh `record`. Both directions are pinned: `tests/Unit/Cache/GraphUpdaterTest.php::test_an_edge_to_a_gitignored_file_is_dropped` and `::test_an_edge_to_an_untracked_but_not_ignored_file_is_kept`. The `git check-ignore` invocation itself was already production code (`Change\ChangedFiles::filterIgnored()`); it is now a single shared `Change\Git::ignored()` method both callers use, rather than a second way to shell out to git. Fails open throughout, matching this package's existing precedent (`Cache\Fingerprint::isTrackedByGit()`: no `.git` at all ⇒ trust it): no git binary, not a repository, a subprocess error or a timeout all mean "treat as not ignored, record the edge" rather than aborting or discarding data.
  **No new configuration.** An allowlist of source paths was considered and rejected: `.gitignore` (plus `.git/info/exclude` and the global excludes file) is the one, already-composable, fail-safe mechanism for excluding a path from this package, and an allowlist that omitted a real source root (`Modules/`, `packages/`, a custom `domain/`) would produce exactly the false green this package exists to prevent (`src/Select/ResiduePatterns.php`'s own stated principle). If a path should never be an edge, put it in `.gitignore`.
  **Every existing graph is invalidated once.** Both layers change what an edge *means*, so a graph recorded before this fix is contaminated by definition. `Cache\Fingerprint::compute()` gains a new, **unconditional** structural key, `edges_exclude_ignored` (always `true` — never gated on a config flag, unlike `static_declaration_edges`), rather than a bare `SCHEMA_VERSION` bump: `structuralDrift()` always skips the `'schema'` key when comparing fingerprints, so a schema-only bump can never be *named* in a drift report and a user would see every graph discarded with nothing explaining why. This key gets the same one-time forced fresh record, and `phpunit-replay status` names it (`edges_exclude_ignored (drift)`) instead of leaving the cause a mystery.
  **Visibility**: a `record` pass that dropped a git-ignored dependency now says so on its summary line — `N excluded (gitignored)`, shown only when `N > 0` — and `phpunit-replay status` shows, beside the `edges:` line, how many of a currently-loaded graph's edges point at a file that is ignored *right now* (a live check, useful for spotting stale pollution left over from a graph recorded before this fix). The excluded paths themselves are only printed behind `PHPUNIT_REPLAY_DEBUG=1` (`Console\Runner\Warnings::debug()`), matching every other verbose diagnostic this package already gates the same way.
- **Fixed: `graph.json`'s `files` array grew without bound.** `Graph::link()` (`Graph.php:71-88`) only ever adds to `$files`/`$fileIds` (id ↔ path); nothing else in the class ever removed an entry — not `pruneMissingDependencies()` (`prune --stale-edges`), not `pruneMissingTestFiles()` (which runs automatically on every `run`/`record` where anything changed, `RunPipeline.php:1017`, `ReplayState.php:772` — not only under `prune`), not `replaceEdges()` dropping a stale source on a partial re-seed. `encode()` wrote out every entry unconditionally regardless, so a project's persisted graph carried the path of every source file ever linked to any test, including ones nothing has depended on for months, forever. `encode()` now resolves each id `$this->edges` still points to back to its path and writes only the files whose path is still referenced (everything else about its output is unchanged, including that every id is still renumbered by sorted path on every call, as it already was); **the persisted `files` array can now shrink between runs where it previously never could.** The filter is keyed on path rather than id deliberately, found in review: `link()` itself can never assign two ids to the same path, but `decode()` trusts a `files` JSON array verbatim with no de-duplication, so a foreign/older/hand-edited `graph.json` can hold one path under two ids — and an id-keyed filter (an earlier version of this fix) checks the wrong one of the two (`array_unique()` keeps the first id for a duplicated path, `array_flip()` — what `decode()` builds `$fileIds` from — keeps the last) and would silently drop a live edge instead of remapping it, rather than fail loudly. `test_encode_keeps_an_edge_to_a_path_duplicated_under_two_ids()` pins this with a hand-built duplicate-id payload, the only way to reach that state. The in-memory `$this->files`/`$this->fileIds` (and so `files()`/`stats()['files']`) are deliberately left as they were, uncompacted: no current caller ever reads them between a prune and a save on the same `Graph` instance — the only two call sites that print `stats()['files']`, `RunPipeline::printRecordSummary()` and `ReplayState`'s record-mode summary line, always run against a freshly built graph that cannot yet contain an orphan — and `files()`'s existing contract (every path ever linked, orphaned or not) is already the behaviour `test_replace_edges_replaces_rather_than_unions_and_dedups()` asserts. Physically compacting those two arrays in place would additionally require reworking `link()`'s `count($this->files)`-based id assignment, which silently collides with a still-live id once an entry has been removed by `unset()` — a materially bigger, riskier change for a benefit no reachable call site needs today. Both boundaries are now pinned by tests (`GraphTest`'s new `test_encode_drops_a_dependency_orphaned_by_*` and `test_stats_files_counter_still_counts_an_orphan_until_the_next_encode`) so a future change cannot cross either silently.
- **Removed a class of bug in the CLI's own argv parsing, rather than only guarding against it.** `Application`'s argv pre-splitter (`splitPassthrough()`) used to decide which CLI tokens belonged to phpunit-replay itself from five hand-maintained constants (`COMMAND_NAMES`, `OWN_LONG_OPTIONS`, `GLOBAL_LONG_OPTIONS`, `GLOBAL_SHORT_OPTIONS`, `PARALLEL_SHORTCUT_COMMANDS`) plus two hardcoded `--option=value` special cases and a literal-string `-p`/`--parallel` check — five separate copies of information Symfony's own command/application `InputDefinition` objects already hold, kept in sync by hand. Missing an update here doesn't just drop the missing option: the splitter is a latch, not a per-token test (once one token is unrecognised, everything after it — including a real option typed later on the same line — goes to PHPUnit too), so one missed entry has twice caused a whole command to fail: `prune --remote/--keep-months/--squash` (added in `e9e428a`, fixed 18 minutes later in `91e8c1d`), loudly (`prune` declares no positional argument, so Symfony threw "Too many arguments"); `verify --parallel` (`7e06b07`), silently (`verify` has an `IS_ARRAY` `phpunit-args` argument to swallow it into, so the suite ran single-process while reporting nothing wrong).
  `splitPassthrough()` now reads `Command::getNativeDefinition()` and `Application::getDefinition()` directly instead: a command's own options/shortcuts, the global ones every command inherits, and `InputOption::isValueRequired()`/`isValueOptional()` for the value-mode special cases — subsuming all five constants and both hardcoded special cases, with nothing hand-maintained left to drift. Confirmed live while writing the characterization corpus this replaced: the previous `GLOBAL_LONG_OPTIONS` constant was itself already missing `--silent`, a global option Symfony 8.1 added that a hand-written list had no way to know about — the exact class of bug this removes, already shipping. `tests/Unit/Console/ApplicationArgvSplitTest.php` (a 100+-case data-driven corpus generated by running the previous implementation and reading every case back by hand) supersedes and deletes `ApplicationOwnLongOptionsTest` — a regression guard added and shipped only within this same Unreleased window, which asserted the five constants agreed with each command's real definition: once the constants are gone that guard would be vacuous, comparing a thing with itself. Pinning observable argv-splitting behaviour is strictly stronger than pinning internal consistency between two hand-written copies of the same fact, since the latter cannot fail when both copies are wrong the same way.
  Short-option recognition (`resolveShortToken()`) is a general two-level rule — Symfony's own multi-alias shortcut keys first (`--verbose`'s `-v|-vv|-vvv`, already exact matches, no regex needed), then a single shortcut character with anything left over owned as its glued value whenever that shortcut `InputOption::acceptValue()`s — so `-p4`/`-p10` (a process count glued directly onto `-p`, no `=`) needed no name-specific regex to keep working and remain recognised exactly as before. The same rule additionally fixes `-p=2`, previously NOT recognised despite both SPEC.md and README documenting the option as `-p[=N]`: confirmed empirically that Symfony's own `ArgvInput` does not strip a glued `=` itself either (`-p=2` parses to the literal value `"=2"`, which fails `RunRequest::parseParallel()`'s numeric check and silently falls back to Paratest's auto-detected count) — so the splitter now rewrites `-p=2` to `-p2` when it emits the token, which Symfony does parse correctly, mirroring how `=` already works for the long form (`--parallel=2`). One gap remains pinned, not fixed, as a genuinely separate, out-of-scope rule (a long-option next-token peek, follow-up work): `--log-junit`/`--keep-months`'s bare two-token form (`--log-junit result.xml`) is still not recognised, only `--option=value` is.
- **Correctness fix: a Laravel migration, seeder or console command could hold a coverage-derived edge that many real dependents shared but only ever one of them was credited with — and editing the file then re-ran only that one.** The property that actually decides this, and the wrong one to check: not "two parallel passes agree" but **serial vs. parallel**, the two extremes of first-loader attribution. Serial (one process for the whole suite) makes a once-per-process body execute exactly once in the entire run, crediting the minimum possible — one test; 8-worker parallel executes it once per worker, crediting up to eight; full process isolation would credit every test that triggers it. Measured directly on a real 9,056-test Laravel project, both with `static_declaration_edges` on and with it off: a serial `record` produces 60,282 edges, an 8-worker parallel one 60,572 (**+290**), and **95 of 726 test files have a different dependency set between the two shapes** — two parallel passes agreeing (already pinned for the declaration/first-loader case) proves far less than it looks, because serial is reproducible precisely by making one deterministic arbitrary choice every time. Of **381** such shape-dependent attributions, **223 (58.5%)**, over **16** files (4 migrations, 7 seeders, 5 console commands under `app/Console/Commands/*`), have the shape this fix closes: `Analysis\DeclarationScanner` classifies all 16 as having function bodies, none declaration-only, so this is not the first-loader problem `static_declaration_edges` already fixes — these bodies genuinely execute once per **worker process** (a migration runs once per worker database, a seeder once, a console command's registration once), guarded the same way Laravel's own `RefreshDatabaseState::$migrated` guards a migration, and whichever test triggers that in a given worker is credited. **138 of the 726 test files (19%) hold an edge to at least one of 141 such files** (the five console commands alone carry 129 holders each). `Graph::unionEdges()` keeps this from ever *losing* an edge already captured, but Paratest's work distribution is not resampled at random between recordings — the same test lands in the same worker every time for a fixed worker count — so a test that never once happens to be first in any of those runs never receives the edge at all, no matter how many times the suite is re-recorded. That is a real false green, not merely a residual: if a 130th test genuinely depends on such a file, editing it re-runs nothing for that test.
  `Cache\GraphUpdater::apply()` now refuses to record a coverage-derived edge to a file under `database/migrations/`, `database/seeders/` or `app/Console/Commands/` (new `Laravel\OncePerProcessPaths`, a plain exact-case prefix match — no filesystem access, no Illuminate, no application boot). The file keeps no `fileId`, landing it in `Select\ResiduePatterns`' existing no-`fileId` bucket, so a change to it now selects **every test the graph knows** via `Select\Rules\WatchRule` instead of whichever one test a worker happened to credit. Gated on `static_declaration_edges`, exactly like the body filter it sits beside, and re-checked inside `GraphUpdater::apply()` itself (not only at the two construction sites that build the classifier): with the flag off there is no `Select\ResiduePatterns` net to catch a refused edge, so refusing it would be a strictly worse false green than the one this closes, and the code deliberately cannot do that even if a future caller got the construction site wrong. The static half is untouched on purpose: a test whose own source names one of these files (rather than merely triggering it via coverage) still gets the edge through `Analysis\StaticEdges::expand()`'s existing "the test's own file" hop, because a name reference is order-independent evidence and coverage attribution is the only half of the two that is not — the two edge writers this package has are treated asymmetrically here, unlike the git-ignore fix above, which refuses both identically. `tests/Integration/OnceProcessResidueParallelTest.php` pins the actual acceptance property — a serial and a parallel (`-p 4`) recording of the identical tree, resolved to `test file -> dependency path` pairs, come out byte-identical — over a hand-built `app/Console/Commands/OnceProcessDemo.php` guarded from the *caller* side (never inside its own method, mirroring `RefreshDatabaseState::$migrated`) and referenced only through a backslash-free, `Analysis\FactsVisitor`-unparseable string assembly, so the static hop cannot quietly supply the same edge and make the test pass unfixed.
  **This cost is real, not free, and not rare**: measured from the project's own git history, **318 of the last 1,530 commits (20%) touch one of the three directories** — 151 a migration, 200 a console command, 9 a seeder — so roughly **one run in five** now runs the whole suite instead of the fast lane, at an expected cost of about **one minute per run** on a suite whose 8-worker `record` takes 5m05s. **Considered and rejected**: pointing the existing `Hermeticity\Policy` `never_cache` mechanism at the 138 holder test files instead. Same cost in expectation (19% of test files always running either way), but it does not produce a unique graph — the disputed edges stay recorded, so content keys keep moving between machines and the remote cache stays exactly as unshareable as before. Refusing the edge changes what the graph *is*; exempting the tests would only have changed which ones run, at the same price, leaving the actual non-determinism in place.
  **Not closed, and said plainly rather than implied otherwise**: of the 158 attributions over 37 files this fix does not reach, most are declaration-only and already handled by `static_declaration_edges`'s static hop; two have real bodies and are genuinely uncovered — `app/Services/Profiles/PhoneNormalizer.php` (+17 tests) and `app/Services/Publisher/Publication/PublisherUnpublishService.php` (+16). Nothing about their path says "executes once per process" the way a migration's does, so classifying by path is not an option for them, and — checked, not assumed — their instability is **unexplained**: neither uses a `static` variable, `??=`, or a static property of its own, so on a reading of `Record\Recorder::filesWithExecutedLines()` and `Analysis\FileFacts::coversAnyBodyLine()` neither should be able to move at all. Recorded as an open question rather than papered over. A live Illuminate container is also deliberately never consulted to resolve any of this (considered and rejected: `GraphUpdater::apply()` runs both from the wrapper process, with nothing loaded, and in-process, with Laravel already booted, so an answer that depended on which one handled a given recording pass would reintroduce the exact process-shape-dependent non-determinism this fix removes, one level up). A project with an unconventional migration layout (`Modules/*/Database/Migrations`) is unknown to `OncePerProcessPaths` for the same reason and keeps today's behaviour. **No new configuration key**: the three convention paths are hardcoded, matching this package's existing precedent (`Select\Rules\MigrationRule::isMigrationPath()`) and its stated principle that a path allowlist is unsafe by construction.
  `docs/reproducibility.md` gains a new "Once-per-process residue" section recording all of the above as measured design, plus three things deliberately not in this PR (hash-based invalidation of the git-diff gate, per-method granularity using the body line ranges `Analysis\DeclarationScanner` already caches, and a two-part remote object that stops an object's address from moving every time an attribution does), and two pre-existing hazards that govern the edge/residue partition regardless of this fix (an untracked `phpunit-replay.php`/`phpunit.xml` silently changing the structural fingerprint; whether `prune --stale-edges` has run).

## [Unreleased]

- **Docs: the cost given for `static_declaration_edges` in 0.3.0 describes only half the change, and the omitted half is twenty times larger.** That entry (and `docs/SPEC.md` §4.3.1) reports "+2.84% (1,781 edges)", which is the count of edges the static hop *adds*; it says nothing about the edges the body filter *removes*. Measured on the same 9,056-test Laravel project the figure came from: turning the flag on takes the graph from **61,278 edges to 21,706** — −39,572, **−64.6%** — removing 41,488 coverage edges while adding 1,916. Someone acting on "+2.84%" expects a graph 3% larger and gets one 65% smaller. The 0.3.0 entry is left as written (a changelog records what was believed at the time); the specification and the new document below carry the correction.
  A second consequence the flag's documentation never stated: with it on, `config/*.php` (55 files), `bootstrap/app.php` and `lang/*.php` (4) leave the graph's `files` table entirely, so `Graph::fileId()` returns null for them, `Select\ResiduePatterns` claims them and `Select\Rules\WatchRule` turns that into "run everything the graph knows" — **editing any `config/` or `lang/` file re-runs the whole suite**, 9,056 tests where the flag off would run the ~700 those files held edges to. Safe and deliberate (residue is covered rather than dropped, which is the whole point), but a trade rather than an upgrade, and now stated where someone deciding whether to opt in will read it.
- **The graph is reproducible for a fixed execution shape — measured, not argued.** Two *sequential* `record` passes (no `--parallel`, so one process and Paratest's work distribution removed as a variable) on that same 9,056-test suite produced identical `files`, `edges`, `test_tables`, `not_cacheable` and `fingerprint`, and of the fields on every stored result — status, assertions, message, file and **content key** — only the wall-clock time differed. So **every content key matched**, and the 14–22 residual measured under 8 workers is Paratest's distribution rather than anything in this package's logic or in the suite. That is what makes the single-producer approach viable: a graph recorded once in one shape and distributed with `push --graph`/`pull` gives every machine the same object addresses by construction, without waiting for convergence.
- **And the suite-level assertion variance was one test, not noise.** 35,387–36,299 across parallel passes and 70,241 sequentially, with test/skip/deprecation counts identical every time; subtract `NovaCustomStylesTest::every_registered_style_resolves_to_a_file_that_exists` and the rest of the suite makes **exactly 32,801** in every single configuration. `Nova::allStyles()` accumulates a registration per application boot and never de-duplicates, so a method whose body makes 6 assertions makes 6 × boots-in-this-process: 6 in isolation, ~3,474 in one of eight workers, 37,440 in a single process. Per-test `assertions` from `--log-junit` is consequently **reliable**, including under Paratest — every other test's count matches exactly between the parallel and sequential passes. An earlier reading in the same session mistook that one test's real, boot-dependent count for a log-merging artifact and is corrected here rather than left standing.
- **Added `docs/reproducibility.md`**: the measured answer to whether the dependency graph is a function of the tree or of the run, on that same real suite. Three configurations, every pairwise comparison: **189** differing test files of 726 before the fixes, **78/64/67** with the ignored-edge fix, **22/15/14** with `static_declaration_edges` on as well — and the `files` set, which used to move between passes (2,115 vs 2,082), identical every pass after. It records why this decides whether a remote cache can work at all (`Cache\ContentKey::forTestFile()` puts the dependency list *in* the object key, so two machines that attribute differently cannot find each other's objects — 26% of test files unreachable before, 2–3% after), the measured mechanism of the residual that neither technique can remove (once-per-worker side effects: migrations, seeders, console-command registration — 22 of 22 have function bodies, so this is not the declaration first-loader problem; holder sets *shrink* rather than swap, `129 → 128 → 128`), and why `Graph::unionEdges()` makes that residual a cache miss rather than a false green. Also two measurement traps worth knowing before repeating any of it: per-test `assertions` from `--log-junit` is untrustworthy under Paratest (a method making exactly 6 assertions was reported as 3,474 in the merged XML), and a sequential record of a 9,056-test suite exhausts the 512 MB CLI default at test 6,615.

## [0.4.0] — 2026-09-09

- **`verify`'s `would replay` figure was measured in a way that could not answer the question the README told people to act on — the old wording promised something the old code could not deliver.** The README presented it as the figure to watch when deciding whether the fast `run` lane can serve as a per-PR merge gate: how much of the suite that lane would cover. It was measured by comparing each **stored** content key against one **freshly re-observed** on the same pass (`RunPipeline::verify()`'s `$wouldReplay` loop skipped a test whenever `$oldKey !== $newKey`). But `verify` re-records edges, and `Graph::unionEdges()` only ever grows a test file's dependency set, so any test that gained an edge on that very pass got a new key and dropped out of the count. What the figure answered was *"is this test's dependency set byte-identical to the last recording?"* — a question about the graph's convergence, not about the fast lane. It therefore depended on how many passes had run rather than on the tree: on a real 9056-test suite `9056 − would replay` fell 2001 → 1941 → 1502 → 1253 across four identical full passes (and 1135 → 1032 on the 0.3 line with `static_declaration_edges` on, from a fresh graph), monotonically shrinking and never converging, while `run` on the same unchanged tree replayed 9056 of 9056 — because `run` never re-observes anything, it reads the stored keys. It was wrong in the opposite direction too, on a change that moves no key at all: creating a watched-but-uncovered file (a `.env` matches a default watch pattern) puts every test file in the run list, so a `run` there replays nothing, yet the key comparison happily reported the whole suite as "would replay". This is the third and last defect in that loop; the two earlier ones (iterating the whole cached corpus, and `verify --filter` rewriting the graph, both fixed above) were arithmetic — this one was the measurement design.
  It is now decided the way `run` decides it, by the same code. New `Select\ReplaySet` reads the run list `Select\RunListBuilder` produces and counts every cached result whose test file is **not** in it and still exists on disk. Run-list absence is almost the whole rule, because the run list already holds the affected selection plus the unknown/rerun/quarantined/not-cacheable buckets, so a surviving file is exactly one `ReplayState::decideFresh()` reaches its cached-result branch for. The disk check covers the single exception — a *deleted* test file, which is in no bucket either (they are all built from a directory walk or an `is_file()` check) and so was absent from the run list for the one reason that does not mean "replayable". `run` had always masked that by pruning before building its list (deleting a test file is itself a change, so `pruneResultsForMissingFiles()` runs), so this incidentally removes a latent over-count from `run`'s own replayed figure for any pass that reaches the list unpruned. `RunPipeline::replayedAgainst()` — the figure `run` and `run --dry-run` report as replayed — now reads that same class, so the two numbers cannot drift apart. Content keys play no part in the decision, matching `decideFresh()`, which reads a cached result straight out of the graph and never compares a key (the key addresses the *remote* object store). The decision is computed **before** the PHPUnit child is launched rather than reconstructed afterwards: `apply()` rewrites the graph's edges, keys and results in place, and the run list comes from a git diff plus a directory walk, which after the run would read a working tree the suite (and the generated `.phpunit-replay.xml`) had already changed. A partial CLI selection no longer collapses the figure to 0 either — it narrows which tests the figure is reported over, not the run list it is decided against. `would replay` is now a property of the tree, so two `verify` passes over an unchanged tree report the same number by construction rather than by luck; `tests/Integration/VerifyWouldReplayMatchesTheRunListTest.php` pins that against a new fixture (`tests/Fixtures/Projects/keydrift`) whose observed dependency set grows between passes, and which reported `2 would replay` then `4 would replay` from identical inputs before this fix.
- **New `unverified` figure on `verify`'s summary line**, so that the population divergence detection silently exempts is stated instead of absorbed: `Verify  ✓ 1240 tests · 1198 would replay · 0 divergences · 0 unverified (lifetime: 2 in 143 runs)`. Divergence detection itself is deliberately unchanged — it still compares only results whose stored and re-observed keys match, which is the trustworthy half of the line (0 across six passes on that 9056-test suite) and errs the safe way, since it also checks tests `run` would have re-executed anyway and so can only over-report a divergence, never miss one. What it cannot check is a test whose key moved. `run` would still have served that test's cached result, so it is precisely the part of `would replay` a pass is not vouching for — and it used to disappear into the old count rather than be reported. `unverified` counts it. It settles to 0 as the graph's edges stop moving, and never affects the `✓`/`✗` symbol or the exit code. Noted for a future release and deliberately not changed here: because `run`'s local replay path never compares keys at all, the key-equality gate on divergence detection has no counterpart in the behaviour it models, and dropping it would let `verify` check the cached result of every test that would be replayed — at the cost of moving the divergence number, the one figure on that line currently known to be trustworthy.

## [0.3.0] — 2026-09-08

- Added `static_declaration_edges` (opt-in, **default off**): a second source of dependency edges, derived from static name references rather than from coverage. A coverage driver can only attribute a file it saw execute, and PHP runs a file's top level once per process, so a declaration — an enum's cases, a constants class, an interface, a `return [...]` config — is credited to whichever test in that process loaded it first, and to no other. Measured on a real 9056-test suite, one enum was credited to 8 tests of which only 2 mentioned it, while 21 test files referenced it directly: editing it re-ran none of the other 19. `Graph::unionEdges()` (above) stops such an attribution from being *lost*; it cannot create one that never existed. This adds the missing half. A php-parser pass classifies every source file and records its function-body line ranges, cached under `<stateDir>/analysis/v<RULES_VERSION>/`; a coverage edge then counts only when executed lines fall **inside** a body, which is order-independent because every caller runs those lines every time; and a file that declares a name becomes a dependency of the tests that name it. What neither mechanism reaches — `config/`, `lang/`, a file declaring nothing, a file php-parser cannot read — keeps the conservative residue fallback rather than being dropped, since dropping it is the very false green this exists to prevent.
  The hop is deliberately asymmetric, because indexing every declaring file symmetrically cost **+105.54%** edges on that suite (62,743 → 128,962), 60% of it from five files that merely *register* classes and are behavioural dependencies of 700 of 726 tests: a target with no body gets the full hop (test file plus its behavioural dependencies), since coverage can never attribute it; a target with bodies is reachable only from a test's own source, since every caller already gives it a behavioural edge. Measured cost of the shipped form: **+2.84%** (1,781 edges), median dependencies per test 82 → 84, and those five files contribute exactly zero. Classification costs 3.4s cold and 0.26s warm on 2,195 files.
  The flag and `DeclarationScanner::RULES_VERSION` both participate in the **structural** fingerprint, but only while the flag is on: turning it on or bumping the rules changes what an edge *means*, so it discards the graph deliberately rather than silently mixing two edge semantics, and `status` names which of the two drifted. Projects that never opt in are untouched — with the flag off the suite is byte-identical to the previous release.
  Known limitation, documented at `Recorder::filesWithExecutedLines()`: `XdebugDriver` starts coverage without `XDEBUG_CC_UNUSED`, so xdebug never reports an unexecuted line and the inherited Pest exclusion cannot fire under it, meaning the body filter removes more edges under xdebug than under pcov. Because edges are unioned, a mixed pcov/xdebug CI matrix converges on the union of what the two attribute, never the intersection.

## [0.2.0] — 2026-09-08

- Fixed: correctness — re-recording a subset of tests (`run`, `verify`, in-process replay) could silently drop a test's dependency edge instead of keeping it. A coverage driver attributes a file's declaration footprint (class/enum/const, or any top-level statement) to whichever test happened to load it first in that process, so a partial re-record whose attribution differed from a previous, complete one could make a test's content key stop including a file it still genuinely depends on — a false green: editing that file no longer changed the key, so the stale cached result kept being replayed instead of the test ever running again. `GraphUpdater::apply()` now unions a re-record's edges into the graph (`Graph::unionEdges()`) instead of replacing them (`Graph::replaceEdges()`, still used to seed/replace a graph's state directly); a genuinely stale edge is shed by the next full, fresh `record`, which always starts from an empty graph. Laravel's per-test table tracking (`replaceTestTables`) is unaffected — it comes from a live query listener re-attributed on every run, not a load-once coverage artifact.
- Added `prune --stale-edges`: now that edges only ever accumulate (previous entry), a dependency a test genuinely stopped needing had no way to leave the graph short of a full, fresh `record` — on a large suite the expensive operation people avoid — and lingered forever, changing the test's content key (and forcing an unneeded re-run) every time that unrelated file changed. `--stale-edges` (`Graph::pruneMissingDependencies()`) drops a single dependency edge, inside a test file that still exists, when the dependency's own file is confirmed gone from disk — the one staleness signal that cannot misfire regardless of run order or which test a coverage driver's first-loader-wins attribution happened to credit: "not observed by a recording pass" is never treated as evidence of staleness (`Graph::unionEdges()`'s docblock explains why that would be unsound — same reasoning, mirrored), only "the file itself does not exist" is, so a live dependency can never be removed by this. Deliberately opt-in rather than folded into the no-flag default (`pruneMissingTestFiles()` + `--branches`): those prune purely historical state with no bearing on cache validity, while a dependency edge is exactly what a changed file is matched against to decide whether a cached result can still be trusted, so trimming one — even by a rule this narrow — stays behind an explicit flag the user opts into, same as `--flaky`.
- **Fixed: silent loss of every dependency edge and coverage snapshot on `phpunit/php-code-coverage` 14.3.** 14.3 changed the shape of `ProcessedCodeCoverageData::lineCoverage()` without touching its signature: per line, the value went from a `list<test id>` to an `array<test index, hit count>`, with the ids moved out to a new `testIds()` accessor. Code written against the old shape doesn't error against the new one — it just finds no strings to match and concludes nothing executed. Before this fix that meant every `--coverage-*` run under cc 14.3 silently recorded an empty dependency graph (TIA would conclude nothing depends on any source file) and an empty coverage snapshot, with no exception and no warning anywhere. Fixed by reading the shape off the data itself (a string value means an inline id, an int key with an int value means an interned index) rather than off a version number — see `Coverage\LineHits`.
- PHPUnit 13 fully supported: constraint widened to `^11.5 || ^12.0 || ^13.0` (previously `~13.0.0`, which admitted only the 13.0 line). This package's own PHP floor is unchanged (`^8.2`); PHPUnit 13 itself requires PHP >=8.4.1, PHPUnit 12 requires PHP >=8.3, same as before. `Manuglopez\Replay\PHPUnit\ConfigurationReader` already dispatched across 11.5/12/13.0's test-suite-name getters; no further change was needed there for 13.1-13.3.
- Added `src/Coverage/`, a format-abstraction layer so the rest of the package never has to know which `phpunit/php-code-coverage` is installed: `CoverageFormat` (capability detection, by reading classes/constants/first-line file markers, never by trusting a version constraint) and `CoverageArchive` (the `--coverage-php` reader/writer interface) with two implementations — `LegacyArchive` for cc 11-13's `Report\PHP` shape, `SerializedArchive` for cc 14's `Serialization\Serializer`/`Unserializer` (which also re-expands the relative paths cc 14 writes back to absolute, and reconstructs a `CodeCoverage` object around the plain array cc 14 serializes instead). `LineHits` reads/writes the shape-independent per-line hit data described above. `Snapshot` is this package's own `<stateDir>/coverage/<k>.cov` format, now version-neutral JSON instead of a raw `serialize()` of a `CodeCoverage` object, so a snapshot recorded under one php-code-coverage major keeps merging cleanly under the next.
- **The php-code-coverage 14 line has three mutually-unreadable `--coverage-php` file formats, not one**, distinguished by comparing first-line markers rather than a constant: 14.0/14.1 have no `SERIALIZATION_FORMAT` constant and stamp their own exact version (`// phpunit/php-code-coverage version 14.0.2`), refusing to read any other; 14.2 stamps a format number (`serialization format 1`); 14.3 bumped that number to `3`. A file in a format the installed php-code-coverage cannot read now warns and is copied through unmerged instead of corrupting or failing the run (`CoverageMerger::merge()`).
- `Fingerprint` (`src/Cache/Fingerprint.php`) gained an `environmental.coverage` key (`Coverage\CoverageFormat::id()`, e.g. `cc14/fmt3/snap2`): a recorded result is only replayable while its stored coverage snapshot is still readable, and without this key nothing noticed a cache recorded under one coverage format being read back as silently missing coverage under another. `SCHEMA_VERSION` was deliberately NOT bumped for this: it lives in the structural bucket that feeds every content key, and bumping it would discard every dependency graph on every machine; the environmental bucket clears cached results while leaving the graph's edges standing.
- `NullCoverageDriver` (`src/Report/NullCoverageDriver.php`) now declares `name()`, `version()` and `nameAndVersion()` to satisfy both the pre-14 and 14+ `Driver` abstract surfaces, and its `stop()` calls `RawCodeCoverageData::fromXdebugWithPathCoverage()` — the only factory present on that class across cc 11 through 14.3 (`fromXdebugWithoutPathCoverage()`, what it used to call, is gone in 14.3; `fromLineCoverage()`, 14.3's replacement, doesn't exist before it). The driver's name/version are now constructor parameters, so a merged `--coverage-php` file can keep naming the driver that actually collected the data (cc 14's own `Serialization\Merger` refuses to merge files whose driver information disagrees).
- Git information is deliberately dropped from a merged `--coverage-php` output: a merged file spans several runs at potentially several commits, so stamping it with the working tree's current commit would assert something untrue about it.
- Known trade-off, confined to one class: the cc-14-only calls inside `Coverage\CoverageFormat` (`Serialization\Serializer`/`Unserializer`, `ProcessedCodeCoverageData::testIds()`/`setTestIds()`/`collectsHitCounts()`, none of which exist before cc 14 or 14.3) are dispatched through non-literal class/method names rather than imported, because PHPStan can neither introduce a class/method that doesn't exist in the installed version via a stub file, nor avoid calling one branch of a literal `class_exists()`/`method_exists()` guard dead against whichever version happens to be installed. That is a real, deliberate loss of static checking on those calls, covered instead by `tests/Unit/Coverage`.
- The PHPUnit 13.3 `--repeat`/`--retry` test-id hazard (`#[Repeat]`/`#[Retry]` making `PHPUnit\Event\Code\TestMethod::id()` non-stable — repetition/attempt-suffixed — across runs that differ) is now reachable, since 13.1+ is supported, and is now covered both ways it arises: a `--repeat`/`--retry` **CLI flag** degrades the *whole run* to a plain, unreplayed, unrecorded PHPUnit invocation (`ConfigurationReader::repeatOrRetryRequested()`, checked by `RunPipeline` and `ReplayExtension::bootstrapInProcess()`), since that hazard is global to the run it appears on; a `#[Repeat]`/`#[Retry]` **attribute** — which PHPUnit's own `TestBuilder` honours on every run regardless of any CLI flag, so a decorated method would otherwise be silently replayed wholesale from a prior recording — is instead excluded **per test**: `RecordRepeatOrRetryNotCacheableOnPreparationStarted` marks exactly the decorated method's current id (whatever repetition/attempt suffix it carries, including the bare, unsuffixed one a first repetition/attempt always gets) not-cacheable, the same way a `#[NotCacheable]` entry is, so the rest of the suite still replays normally.
- Package CI: the `test` job's matrix moves to PHP 8.2/8.3/8.4 × PHPUnit `^11.5`/`^12.0`/`^13.0` × pcov/xdebug (12 of 18 cells, same exclusions as before, now against `^13.0` instead of `~13.0.0`). A new `coverage-format` job additionally pins PHPUnit at 13.1.14 and forces `composer update --with phpunit/php-code-coverage:<minor>.*` for 14.0, 14.1 and 14.2 in turn (3 more cells) — `^13.0` alone resolves straight to cc 14.3 and would leave the other three file formats untested. 15 cells total.
- Docs: README, `docs/SPEC.md`, `docs/INTERNALS.md` and `docs/README.md` updated to state full PHPUnit 11.5/12/13 support; the stale "13.1+ not supported" claim and its php-code-coverage `^14` reasoning are removed.
- `--parallel`/`-p` on a Laravel project invoked `vendor/bin/paratest` directly, without Laravel's
  own `--runner=\Illuminate\Testing\ParallelRunner` or `LARAVEL_PARALLEL_TESTING=1`: every worker
  migrated the SAME database instead of a per-worker one, surfacing as
  `ERROR 1213 (40001) Deadlock found when trying to get lock` on `DROP TABLE` rather than a clean
  test failure. Both are now wired up automatically whenever Laravel, Paratest, and a resolvable
  `Illuminate\Testing\ParallelRunner` are all present (`Laravel\ParallelIsolation`); opt out with
  `laravel_parallel_isolation: false`. Degrades with a warning — never a crash — when the project's
  Laravel application can't be resolved, or when Paratest is present but `ParallelRunner` isn't.
- The `laravel-lite` fixture's `sqlite :memory:` configuration is why the package's own suite never
  caught this (every worker already gets its own isolated database by construction); a second,
  file-based-sqlite testsuite (`tests/ParallelFileDb`) now proves real per-worker database
  separation end to end.
- Fix `run --dry-run` executing the full suite instead of printing the plan: `RunPipeline::runRecord()` (no cached baseline yet), `degrade()` (the single funnel for every "fall back to a plain PHPUnit run" case — no coverage driver, environment resolution failures, an unexpected exception) and `runResultsOnly()` (a partial CLI selection: `--filter`/`--group`/`--testsuite`/an explicit path) now honour `--dry-run` themselves instead of only the replay branch, printing a plan line to stdout and exiting 0 without ever launching PHPUnit or writing state.
- Fix `verify` silently ignoring `--parallel`/`-p[=N]`: the option was never declared on the command and the argv splitter forwarded it straight through to PHPUnit as a passthrough argument; `RunPipeline::verify()` also constructed a `PhpunitProcess` directly instead of going through the branch that picks `PhpunitProcess`/`ParatestProcess`. `verify` now supports `--parallel`/`-p[=N]` exactly like `run`/`record` and actually runs through Paratest — the difference that matters most, since `verify` runs the full suite and is the command the README recommends as the PR merge gate.
- **Data-integrity fix**: `verify` carrying a partial CLI selection (`--filter`/`--group`/`--testsuite`/an explicit path) unconditionally rewrote the graph's edges from a run that never covered the suite, pruned every sibling result the selection excluded, and published a baseline sha for a partial run — reported from a real 9056-test suite as two identical back-to-back `verify` runs claiming "would replay" of 6304 and then 9056. `RunPipeline::verify()` now derives `recordsEdges` from `hasPartialSelection()`, the same guarantee `run`'s results-only path already gave a partial selection. The same fix corrects the "would replay" counter itself, which iterated the whole cached corpus instead of the tests this run actually executed — an untouched entry trivially matched itself, so the figure could exceed the "N tests" printed beside it and disagreed between two otherwise-identical runs; it now iterates only `$partial->results`.
- `record` now exits `2` when it degrades to a plain PHPUnit run and that run itself reported success (exit `0`): a degrade never writes a graph or even the state directory, so forwarding PHPUnit's own "0" straight through made a `record` that recorded nothing indistinguishable from one that succeeded (reported: a removed PHPUnit method degraded a CI `record` step, which then ran all 9056 tests, printed a normal summary, and exited 0 with nothing on disk — noticed only by manually checking for the state directory). `run` is unaffected: its exit code is still PHPUnit's own regardless of whether it degrades, per the documented "never change PHPUnit's exit code" guarantee, since unlike `record`, `run`'s exit code is the actual pass/fail signal CI gates on.
- **Data-integrity fix, and a hole in the guarantee directly above**: `record` carrying a partial CLI selection (`--filter`/`--exclude-filter`/`--group`/`--exclude-group`/`--testsuite`/`--exclude-testsuite`/an explicit path) silently took the results-only branch meant for `run` — `RunPipeline::run()` (the entry point `record` shares with `run`; `RecordCommand` just sets `RunRequest::$record = true`) checked `ConfigurationReader::hasPartialSelection()` before ever looking at `$request->record`. That branch writes no edges, publishes no baseline, and prints no warning, so `record -- --filter=X` executed and returned PHPUnit's own exit code with nothing recorded — the same silent-loss-of-the-whole-feature failure class as the two fixes above, and specifically unreachable by the `record`-degrade exit code immediately above it, since results-only mode is a deliberate destination for `run`, not a degrade. A partial run cannot produce the one thing `record` exists to produce — pruning and the published baseline sha both assume the whole suite ran — so `RunPipeline::resolveEnvironment()` now refuses this combination outright, before the graph is even loaded, by degrading exactly like every other reason it cannot proceed: the user's selection still runs for real via the plain, unwrapped PHPUnit fallback (the run is never silently skipped), the graph is left completely untouched, and the existing "degraded `record`" rule above turns a passing fallback into exit `2` instead of a false `0`. `run`/`verify` are unaffected — only `$request->record` reaches the new check — and keep handling a partial selection exactly as before (`runResultsOnly()`, `verify()`'s own `hasPartialSelection()` gate). Also checked, and found unnecessary: `runResultsOnly()` has no missing-coverage-driver check the way `runRecord()`/`verify()` do, because it never needs one — it always runs with `$iniFlags = []` and always calls `GraphUpdater::apply(..., recordsEdges: false, ...)`, so no coverage data is ever collected or required; adding one would only break `run --filter` on driver-less machines (SPEC §16 acceptance criterion 7) for no correctness gain.
- **Visibility fix, in-process mode's equivalent of the gap directly above**: a project configured with the standing `mode: record` (SPEC.md §6.1) also silently lost its baseline refresh whenever a developer ran `phpunit --filter=X` directly (no wrapper) — `ReplayState::decideMode()` checks `hasPartialSelection()` before `config->mode === 'record'`, downgrading to `Mode::ResultsOnly` with nothing said. Unlike the wrapper's own `record` command, refusing outright is the wrong fix here: `mode: record` is a standing configuration, not a one-shot imperative, and a developer running a filtered suite mid-session is doing an entirely ordinary thing — downgrading to results-only is the *correct* behaviour, it is what stops a filtered run from silently writing a partial baseline. What was missing was only that nothing said so. Considered and rejected: an unconditional `Warnings::warn()` on every such run (in a `mode: record` project this could fire on most filtered runs during normal development — a warning people learn to ignore is worse than none) and a `Warnings::debug()`-gated one (invisible unless `PHPUNIT_REPLAY_DEBUG=1` is already set, so it never reaches someone who doesn't yet know to look for it — the exact person confused about why their baseline never refreshes). Instead: the summary line the extension already prints unconditionally once per in-process run (`ReplayState::summaryLine()` → `Report\Summary::format()`) now gains a `record mode: baseline NOT refreshed (partial selection)` segment when `decideMode()` recorded that a standing `mode: record` — not just `auto`'s ordinary "no baseline yet" — was what the selection defeated (`ReplayState::$recordModeDowngraded`, `Summary::$recordModeDowngraded`). This costs no new noise channel: the line was always going to print. The wrapper's `run --filter` (and `run`'s own `mode: auto` first-run bootstrap) are both completely unaffected and stay exactly as silent as before.
